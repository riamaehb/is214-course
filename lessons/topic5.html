Data Types & Type Systems

Topic 4 ended with AST → evaluation → value. Now we can ask the next question: what kind of value is this, and what operations are valid for it?

Types are how a programming language classifies values and determines what you can do with them. We'll keep this practical and interpreter-oriented: enough type-system thinking to build a working evaluator, without turning this into a formal type-theory course.

By the end of this topic, you should be able to

  • explain the relationship between values, types, and valid operations;
  • predict the type an expression produces, not just a literal;
  • distinguish static and dynamic typing;
  • explain what type checking does, using simple type rules;
  • distinguish explicit conversion from implicit coercion;
  • explain type inference conceptually;
  • describe Python's own type system precisely; and
  • explain why type annotations don't make Python statically typed.

Estimated study time: 75–100 minutes.

From Values to Types

2 + 3

produces a value. But:

2 + "3"

causes a problem in Python.

So why can a language allow one expression but reject another?

Both have the same basic syntactic shape: something, +, something. The difference isn't syntax. It's what kind of thing each operand is.

What Is a Type?

A type is a classification of values that helps determine which operations are meaningful for them.

42int
3.14float
"hello"str
Truebool
A type tells us what kind of value we're dealing with, and what operations the language allows us to perform on it.

Page 5

Static and Dynamic Typing

Static typingType relationships are checked primarily before execution.
Dynamic typingType relationships are checked primarily during execution.

These describe the typical timing of type checking. They aren't complete definitions of an entire type system — real languages vary in the details.

One trap to avoid: static does not automatically mean "safe," and dynamic does not automatically mean "unsafe." Those are different questions.
Page 6

When Is the Error Detected?

x = 10
x + "hello"

Every character here is a valid token, and the arrangement is valid syntax. expression + expression is perfectly fine structurally. The problem only appears when Python actually tries to add an int and a str together.

In a dynamically typed language like Python, a type problem is usually just a specific kind of evaluation-time problem — not a separate fourth detection stage alongside lexical and syntax errors.

That's not universal, though. Some statically typed languages check many type rules before execution, so a mismatch like this can be caught without running the program at all. Whether a type problem shows up early or late depends on the language — which is exactly what the static-vs-dynamic distinction is about.

Page 7

Type Checking and Type Rules

Type checking determines whether an operation is valid for the types of its operands.

int + intvalid
str + strvalid
int + str?

The language answers that ? using a type rule: a statement of which types an operation accepts and what type it produces:

+ : int × int → int

Read this as: "+ takes an int and an int, and produces an int." The exact rules — including which combinations are allowed — depend on the language.

Page 8

Build: A Small Type Checker

Here's a tiny function that implements one type rule for addition. Notice that it returns a simple Boolean: True if the operation is allowed, False if it isn't:

def can_add(left, right):
    return (
        isinstance(left, (int, float))
        and isinstance(right, (int, float))
    ) or (
        isinstance(left, str)
        and isinstance(right, str)
    )

Now try extending it in your own Python environment:

  • write a similar can_multiply function;
  • try extending the checker to handle Boolean operands — pay attention to how Python's bool relates to int;
  • have it return a simple type-error message instead of just False.
This is deliberately small. We're illustrating the idea behind type checking, not building a complete type system.
Page 9

Conversion and Coercion

Explicit conversionThe programmer requests it: int(3.7), float(3), str(42)
Implicit conversion (coercion)The language performs it automatically: 2 + 3.0

Compare that with 2 + "3", which raises an error instead of silently converting anything. Python coerces between int and float in this context, but it doesn't coerce numbers and strings into a common type for +.

The point isn't to memorize every Python conversion rule. It's to recognize that different languages draw this line in different places.

Observe
Reason through these three: 2 + 3.0, 2 + int("3"), str(2) + "3". What's the same about all three, despite looking different?
In each case, a conversion happens first (one implicit, two explicit), and only then does the actual operation run on operands that now share a compatible type. Conversion doesn't change what + does — it changes what + is being asked to operate on. Once the types match, the same ordinary type rule applies.
Page 10

Type Inference

x = 10

In some statically typed languages, the compiler can infer that x has type int without the programmer writing the type explicitly. It can get that information from the value assigned, and then use it when reasoning about what comes next:

y = x + 2
Does the programmer have to specify the type, or can the language infer it?

Keep this conceptual. We aren't getting into the formal algorithms real languages use to infer types across an entire program.

Predict
Given x = 10 then y = x + 2, versus x = "hello" then y = x + " world" — what can you infer about y in each case? Now consider a single name reassigned: x = 10 ... later ... x = "hello". What's different about this third case?
In the first two cases, y's type follows directly from x's type at that point — int, then str, respectively. The third case is different in kind: it's not asking what type a value has, it's showing that the same name can point to values of different types over time. That's the distinction between the type of a value and a permanent type declaration for a name — Python has the former, not really the latter.
Page 11

Python's Type System

Python is dynamically typed, and it generally does not perform implicit conversions between unrelated types.

Notice what this description avoids: it doesn't call Python "strongly typed." That label gets used constantly, but it doesn't have one universally agreed-on definition. So we'll describe what Python actually does instead of relying on a label that people use differently.

x = 10
x = "hello"
  • x is a name.
  • 10 and "hello" are values.
  • The values have types — int, then str.
  • The name can be rebound to values of different types.
The values have types. Python names are not permanently assigned a static type by ordinary assignment.
Page 12

Type Annotations Are Not Static Typing

x: int = 10

This looks like it should change how Python runs. It doesn't.

So what are type annotations for? They provide information that can be used by:

  • type-checking tools (like mypy);
  • IDEs, for autocomplete and warnings;
  • documentation; and
  • other developers reading the code.
Type annotations do not make Python's normal execution model statically typed. Python does not normally enforce annotations at runtime; type-checking tools can use them to detect potential problems before execution.

This distinction matters in practice: annotated Python code can still raise the same runtime type errors as unannotated code.

Page 15

Check Your Understanding

Six questions to check whether you can apply the ideas from this topic, not just recall definitions. This isn't graded.

1 · Apply it
For x = 3.14, what's the value and what's the type — and why does that distinction matter for what you can do with x next?
The value is 3.14; the type is float. The distinction matters because the type, not the specific value, is what determines which operations are valid — x + 1 is fine because floats support addition, regardless of which particular float x happens to be.
2 · Apply it
A colleague says a language "checks types at compile time." Which of static/dynamic typing does that describe, and what does it imply about when a type mismatch would be caught?
Static typing — checking primarily before execution. It implies a type mismatch like adding an int and a string would be caught before the program ever runs, rather than only surfacing once that specific line actually executes.
3 · Apply it
Given the type rule + : int × int → int, what would type checking conclude about "5" + 3?
Invalid — the rule requires both operands to be int, but the left operand is a str. Type checking would reject this unless the language defines a separate rule (or coercion) covering str/int combinations, which Python doesn't for +.
4 · Apply it
2 + 3.0 and int("3") + 2 both "fix" a type mismatch before combining values. What's actually different about how each one does it?
The first is implicit coercion — Python converts the int to a float automatically, without being asked. The second is explicit conversion — the programmer calls int(...) directly. Same underlying idea (make the types compatible before operating), different mechanism.
5 · Apply it
Given only x = 10, a language with type inference can determine x : int without being told. What has to be true for that inference to work?
The language needs to look at the actual value being assigned (10) and determine its type from that, rather than requiring the programmer to write the type explicitly. Type inference is about the language figuring out type information on its own, not the programmer declaring it.
6 · Apply it
x = 10, then later, x = "hello" — perfectly legal in Python. What does this tell you about what a Python name actually is?
A Python name isn't permanently tied to one type. The type belongs to the value currently being pointed at, not to the name itself — so reassigning x to a value of a different type is completely legal, since nothing about x was ever fixed to int in the first place.
Final synthesis

If Topic 4 asks "what value does this AST produce?", what additional question does Topic 5 make us ask?

What type of value is produced, and is the operation that produced it actually valid for those types?

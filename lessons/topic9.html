IS 214 · TOPIC 9 · STUDY GUIDE

Objects, References, Mutability & Memory

SYNTAX

what is valid

SEMANTICS

what it means

EXECUTION

what happens

Topic 6 established names, bindings, scope, and environments. Topic 7 showed how function calls create environments and bindings. Topic 8 focused on what executes next. This topic asks: what are the runtime objects those bindings refer to, and what happens when multiple names refer to the same object?

Rebinding changes what a name refers to. Mutation changes the object itself.

By the end of this topic, you should be able to

  • distinguish a name, a reference, and an object;
  • distinguish equality from identity;
  • explain aliasing, and predict its effects;
  • distinguish rebinding a name from mutating an object;
  • explain why mutation inside a function can affect the caller's object;
  • distinguish a shallow copy from a deep copy; and
  • explain reachability and its relationship to memory reclamation.

Estimated study time: 90–120 minutes.

Page 2

Objects Have Identity

a = [1, 2, 3]
b = [1, 2, 3]
Same values. Are they the same object?

No — a and b refer to two distinct objects that happen to contain equal values. Every object has:

Identitywhich specific object this is
Value / statewhat it currently contains

Add a third name:

c = a
Predict
Predict each of these: a == b, a is b, c == a, c is a.
a == b → True (equal values). a is b → False (different objects). c == a → True (equal values, and also the same object). c is a → True — c = a didn't create a new object, it bound c to the exact same one a already refers to.
== asks about equality. is asks about identity. The emphasis is on the underlying concepts, not memorizing which operator does which.

References and Aliasing

a = [1, 2, 3]
b = a
a
b
→
[1, 2, 3]
One object can be accessible through multiple names. This is called aliasing.
b.append(4)
Predict
What does a refer to now?
[1, 2, 3, 4]. a and b alias the same object, so a change made through b is visible through a too — there was never a copy to begin with. This is the first real consequence of shared mutable state.
Page 4

Hands-On: Identity and Aliasing

a = [1, 2, 3]
b = a
c = a.copy()

Predict, before checking:

a is b
a is c
a == b
a == c
Predict
What are the four results?
a is b → True (b is an alias of a). a is c → False (.copy() made a distinct object). a == b → True — the same list, so trivially equal to itself. a == c → True — a distinct object, but with contents that happen to be equal.
b.append(4)
Draw it
After this line, sketch the object/reference diagram — how many list objects exist, and which names point to which?
Two list objects exist. a and b both point to the first one, now [1, 2, 3, 4] after the mutation. c points to the second, independent object, still [1, 2, 3] — completely unaffected by b.append(4).
Page 5

Rebinding vs. Mutation

The central distinction of this entire topic. Compare:

Rebinding

a = [1, 2, 3]
b = a
b = [4, 5, 6]

Mutation

a = [1, 2, 3]
b = a
b.append(4)
Rebindingb = [4, 5, 6] points b at a brand-new object. a still points at the original — completely unaffected.
Mutationb.append(4) changes the object b (and a) already point to. Both names now see the change.
Rebinding changes what a name refers to. Mutation changes the object itself.

Given any operation from here on, ask exactly one question: did a binding change, or did an object's state change?

Page 6

Hands-On: Rebinding vs. Mutation

def rebind(items):
    items = ["new"]

def mutate(items):
    items.append("new")

values = ["old"]
rebind(values)
print(values)
Predict
What does print(values) show after rebind(values)?
Correct — inside rebind, items = ["new"] just points the local name items at a new object. values, outside the function, was never touched.
Not quite — that would be true if items.append("new") had run instead. Plain assignment inside the function only rebinds the local parameter name.
values = ["old"]
mutate(values)
print(values)
Predict
What does print(values) show after mutate(values)?
Not quite — items.append mutates the shared object directly, so this change is visible through values too.
Correct — mutate's parameter items refers to the exact same object as the caller's values. append() mutates that shared object, so the caller sees the change.
Both calls create a new parameter binding. Only one of them mutates the object that binding shares with the caller.
Page 7

Mutable and Immutable Objects

A mutable object can have its state changed after creation.
items = [1, 2, 3]
items.append(4)

Lists are mutable — the same object, changed in place. Now contrast:

x = 10
x = x + 1
The integer object is immutable, so it isn't changed. x + 1 produces another integer value, and x is rebound to the resulting object.
Commonly mutablelists, dictionaries, sets
Commonly immutableintegers, floats, strings, tuples

Not a list to memorize — the important question is always the same one from the last page: did the object change, or did the name become associated with another object?

Page 8

Objects and Function Calls

def add_item(items):
    items.append("new")

values = []
add_item(values)
What does values contain after this call?

["new"]. Topic 7 established that a function call creates a new parameter binding — items is a fresh binding, local to this call. But that binding refers to the exact same object that values refers to in the caller. items.append(...) mutates that shared object, so the caller sees the change.

values (caller)
items (call env)
→
["new"]

Resist the label "pass-by-reference" here — that term carries baggage from other languages that doesn't map cleanly onto this. What's actually happening is simpler and more precise: a new binding is created, and it happens to refer to an object the caller can also reach.

Copying

a = [1, 2, 3]
b = a
This creates an alias, not an independent copy.
b = a.copy()

Now there are two distinct list objects — mutating one no longer affects the other.

b = a

alias — one object, two names

b = a.copy()

two independent objects

Page 10

Shallow vs. Deep Copy

a = [[1, 2], [3, 4]]
b = a.copy()
The outer lists are distinct. The nested lists are still shared.
b[0].append(99)
Predict
Does a change?
Yes — a becomes [[1, 2, 99], [3, 4]]. .copy() only copies the outer container; a[0] and b[0] still refer to the exact same inner list object.
A shallow copy copies the outer container, not the entire object graph reachable from it.
import copy
b = copy.deepcopy(a)

A deep copy recursively copies nested objects rather than sharing the same nested objects. The goal here is understanding shared versus independent objects — not memorizing the copy module's API.

Object Lifetime and Reachability

a = [1, 2, 3]
b = a
del a
Predict
Is the list object still around after del a?
Yes — del a only removes the name a. The object is still reachable through b, so it remains fully available.
del b
An object that is no longer reachable through any name can become eligible for memory reclamation.

This connects directly to Topic 6's discussion of lifetime — a binding's lifetime and an object's lifetime are related but not identical questions.

Garbage Collection, Briefly

Garbage collection reclaims storage for objects that are no longer needed.

↓ yes → remains available · no → eligible for reclamation

One real complication, briefly: two objects can reference each other in a cycle (A→B→A) with nothing outside pointing to either. Reference counting alone can't detect that — no implementation detail needed here, just the awareness that reachability isn't always a trivial question to answer.

Resource lifetime

Memory isn't the only resource a program manages — files, network sockets, database connections, and locks all have their own lifetimes too.

Object lifetime and resource lifetime are not necessarily the same thing.

Page 16

Check Your Understanding

Nine questions that ask you to apply this topic's ideas. Not graded — just for you to check where things stand before moving on.

1 · Name vs. object
In x = [1, 2, 3], what is x, and what is the list itself?
x is a name — a binding that refers to something. The list [1, 2, 3] is the object itself, with its own identity and state, existing independently of any particular name that happens to refer to it.
2 · Identity
Given a = [1, 2] and b = [1, 2], why are these two different objects even though they look the same?
Each [1, 2] literal creates a brand-new list object. Nothing about writing the same values twice makes Python reuse the same object — a and b each get their own, independently created and independently mutable.
3 · Equality vs. identity
Given c = a right after the previous question, which of a == c and a is c would be True, and which would also be True for a and b?
For a and c: both == and is are True because they refer to the same object. For a and b: == is True because their contents are equal, while is is False because they are distinct objects.
4 · Aliasing
After b = a, a change made through b is visible through a. Why?
Because b = a didn't copy anything — it bound b to the exact same object a already refers to. a and b are two names for one object, so mutating it through either name is visible through both. That's aliasing.
5 · Rebinding
After b = a, what happens to a if you then run b = [9, 9]?
Nothing — a is completely unaffected. b = [9, 9] points b at a brand-new object; it doesn't touch whatever b used to refer to, and it never touches a at all.
6 · Mutation
After b = a, what happens to a if you then run b.append(9)?
a shows the appended value too. append changes the shared object's state in place — since a and b refer to that same object, the change is visible through either name.
7 · Function calls
A function mutates its parameter with .append(...). Why does the caller's list change too?
The call creates a new parameter binding, but that binding refers to the same object the caller's name refers to — the same aliasing relationship as Page 3, just introduced by a function call instead of an ordinary assignment. Mutating through the parameter mutates the one shared object.
8 · Shallow copy
Why can b = a.copy() still leave a and b's nested lists shared?
A shallow copy only copies the outer container — it doesn't recursively copy every object reachable from it. If a's elements are themselves lists, the copy's elements still point at those same original inner objects, so mutating a nested list through b is visible through a too.
9 · Reachability
After del a and del b (with no other names pointing to that list), what makes the object eligible for reclamation?
It's no longer reachable through any name in any active environment. Reachability is the deciding question for memory reclamation — an object that is no longer reachable becomes eligible for reclamation according to the runtime's memory-management rules.
Final synthesis

Rebinding changes what a name refers to; mutation changes the object itself. How does this distinction connect names, references, objects, function calls, and memory?

Names are bindings recorded in an environment; each binding refers to an object with its own identity and state. Multiple names can alias the same object, so a mutation through one name is visible through all of them — including across a function call, where a parameter binding can alias the caller's object. An object that is no longer reachable through any binding becomes eligible for reclamation according to the runtime's memory-management rules.

IS 214 · TOPIC 9 · STUDY GUIDE

Objects, References, Mutability & Memory

SYNTAX

what is valid

SEMANTICS

what it means

EXECUTION

what happens

Topic 6 established names, bindings, scope, and environments. Topic 7 showed how function calls create environments and bindings. Topic 8 focused on what executes next. Now we ask: what are the runtime objects those bindings refer to, and what happens when multiple names refer to the same object?

Rebinding changes what a name refers to. Mutation changes the object itself.

By the end of this topic, you should be able to

  • distinguish a name, a reference, and an object;
  • distinguish equality from identity;
  • explain aliasing, and predict its effects;
  • distinguish rebinding a name from mutating an object;
  • explain why mutation inside a function can affect the caller's object;
  • distinguish a shallow copy from a deep copy; and
  • explain reachability and its relationship to memory reclamation.

Estimated study time: 90–120 minutes.

Page 2

Objects Have Identity

a = [1, 2, 3]
b = [1, 2, 3]
Same values. Are they the same object?

No. a and b refer to two distinct objects that happen to contain equal values. Every object has:

Identitywhich specific object this is
Value / statewhat it currently contains

Add a third name:

c = a
Predict
Predict each of these: a == b, a is b, c == a, c is a.
a == b → True because their values are equal. a is b → False because they are different objects. c == a → True, and c is a → True because c = a simply bound c to the same object.
== asks about equality. is asks about identity. The emphasis is on the underlying concepts, not memorizing which operator does which.

References and Aliasing

a = [1, 2, 3]
b = a
a
b
→
[1, 2, 3]
One object can be accessible through multiple names. This is called aliasing.
b.append(4)
Predict
What does a refer to now?
[1, 2, 3, 4]. a and b alias the same object, so a change made through b is visible through a too. There was never a copy to begin with. This is the first real consequence of shared mutable state.
Page 4

Hands-On: Identity and Aliasing

a = [1, 2, 3]
b = a
c = a.copy()

Before checking, predict:

a is b
a is c
a == b
a == c
Predict
What are the four results?
a is b → True because b is an alias of a. a is c → False because .copy() created a distinct object. Both a == b and a == c are True because the lists have equal contents.
b.append(4)
Draw it
After this line, sketch the object/reference diagram. How many list objects exist, and which names point to which?
Two list objects exist. a and b both point to the first one, now [1, 2, 3, 4]. c points to the second, independent object, still [1, 2, 3]. The mutation through b does not affect it.
Page 5

Rebinding vs. Mutation

This is the central distinction of the entire topic. Compare:

Rebinding

a = [1, 2, 3]
b = a
b = [4, 5, 6]

Mutation

a = [1, 2, 3]
b = a
b.append(4)
Rebindingb = [4, 5, 6] points b at a new object. a still points at the original, completely unaffected.
Mutationb.append(4) changes the object that b — and therefore a — already points to. Both names now see the change.
Rebinding changes what a name refers to. Mutation changes the object itself.

From here on, ask one question whenever you see an operation: did a binding change, or did an object's state change?

Page 6

Hands-On: Rebinding vs. Mutation

def rebind(items):
    items = ["new"]

def mutate(items):
    items.append("new")

values = ["old"]
rebind(values)
print(values)
Predict
What does print(values) show after rebind(values)?
Correct. Inside rebind, items = ["new"] simply points the local name items at a new object. values in the caller was never touched.
Not quite. That would be true if items.append("new") had run instead. Plain assignment inside the function only rebinds the local parameter name.
values = ["old"]
mutate(values)
print(values)
Predict
What does print(values) show after mutate(values)?
Not quite — items.append mutates the shared object directly, so this change is visible through values too.
Correct. mutate's parameter items refers to the exact same object as the caller's values. append() mutates that shared object, so the caller sees the change.
Both calls create a new parameter binding. The difference is what happens to the object that binding refers to.
Page 7

Mutable and Immutable Objects

A mutable object can have its state changed after creation.
items = [1, 2, 3]
items.append(4)

Lists are mutable: the same object can be changed in place. Now contrast:

x = 10
x = x + 1
The integer object is immutable, so it isn't changed. x + 1 produces another integer value, and x is rebound to that resulting object.
Commonly mutablelists, dictionaries, sets
Commonly immutableintegers, floats, strings, tuples

This isn't a list to memorize. The important question is still the same one: did the object change, or did the name become associated with another object?

Page 8

Objects and Function Calls

def add_item(items):
    items.append("new")

values = []
add_item(values)
What does values contain after this call?

["new"]. Topic 7 established that a function call creates a new parameter binding. Here, items is a fresh local binding, but it refers to the same object that values refers to in the caller. items.append(...) mutates that shared object, so the caller sees the change.

values (caller)
items (call env)
→
["new"]

It's tempting to call this "pass-by-reference," but that term carries baggage from other languages and can obscure what's actually happening. The more precise description is simpler: a new binding is created, and that binding refers to an object the caller can also reach.

Copying

a = [1, 2, 3]
b = a
This creates an alias, not an independent copy.
b = a.copy()

Now there are two distinct list objects. Mutating one no longer affects the other.

b = a

alias — one object, two names

b = a.copy()

two independent objects

Page 10

Shallow vs. Deep Copy

a = [[1, 2], [3, 4]]
b = a.copy()
The outer lists are distinct, but the nested lists are still shared.
b[0].append(99)
Predict
Does a change?
Yes. a becomes [[1, 2, 99], [3, 4]]. .copy() only copies the outer container; a[0] and b[0] still refer to the same inner list object.
A shallow copy copies the outer container, not the entire object graph reachable from it.
import copy
b = copy.deepcopy(a)

A deep copy recursively copies nested objects rather than sharing those same nested objects. The goal here is understanding shared versus independent objects, not memorizing the copy module's API.

Object Lifetime and Reachability

a = [1, 2, 3]
b = a
del a
Predict
Is the list object still around after del a?
Yes. del a removes the name a; it does not destroy the object. The object is still reachable through b.
del b
An object that is no longer reachable can become eligible for memory reclamation.

This connects directly to Topic 6's discussion of lifetime: a binding's lifetime and an object's lifetime are related, but they are not the same question.

Garbage Collection, Briefly

Garbage collection reclaims storage for objects that are no longer needed.
object

↓ yes → remains available · no → eligible for reclamation

One complication, briefly: two objects can reference each other in a cycle (A→B→A) with nothing outside pointing to either. Reference counting alone can't detect that. You don't need the implementation details here; just keep in mind that reachability isn't always a trivial question.

Resource lifetime

Memory isn't the only resource a program manages. Files, network sockets, database connections, and locks all have their own lifetimes too.

Object lifetime and resource lifetime are not necessarily the same thing.

Page 16

Check Your Understanding

Nine questions to check whether you can apply the ideas from this topic. This isn't graded.

1 · Name vs. object
In x = [1, 2, 3], what is x, and what is the list itself?
x is a name — a binding that refers to an object. The list [1, 2, 3] is the object itself, with its own identity and state, independent of any particular name that refers to it.
2 · Identity
Given a = [1, 2] and b = [1, 2], why are these two different objects even though they look the same?
Each [1, 2] literal creates a distinct list object. Writing the same values twice doesn't make them the same object, so a and b each refer to their own independently mutable list.
3 · Equality vs. identity
Given c = a right after the previous question, which of a == c and a is c would be True, and which would also be True for a and b?
For a and c: both == and is are True because they refer to the same object. For a and b: == is True because their contents are equal, while is is False because they are distinct objects.
4 · Aliasing
After b = a, a change made through b is visible through a. Why?
Because b = a didn't copy anything. It bound b to the same object a already refers to. Two names, one object — so mutating it through either name is visible through both. That's aliasing.
5 · Rebinding
After b = a, what happens to a if you then run b = [9, 9]?
Nothing — a is completely unaffected. b = [9, 9] points b at a brand-new object; it doesn't touch whatever b used to refer to, and it never touches a at all.
6 · Mutation
After b = a, what happens to a if you then run b.append(9)?
a shows the appended value too. append changes the shared object's state in place — since a and b refer to that same object, the change is visible through either name.
7 · Function calls
A function mutates its parameter with .append(...). Why does the caller's list change too?
The call creates a new parameter binding, but that binding refers to the same object the caller's name refers to. It's the same aliasing relationship as Page 3, introduced by a function call rather than an assignment. Mutating through the parameter mutates the shared object.
8 · Shallow copy
Why can b = a.copy() still leave a and b's nested lists shared?
A shallow copy only copies the outer container. It doesn't recursively copy every object reachable from it. If a's elements are themselves lists, the copy still contains references to those same inner objects, so a nested mutation through b is visible through a too.
9 · Reachability
After del a and del b (with no other names pointing to that list), what makes the object eligible for reclamation?
It's no longer reachable through any active binding. Reachability is the deciding question for memory reclamation: an object that is no longer reachable becomes eligible for reclamation according to the runtime's memory-management rules.
Final synthesis

Rebinding changes what a name refers to; mutation changes the object itself. How does this distinction connect names, references, objects, function calls, and memory?

Names are bindings recorded in an environment, and each binding refers to an object with its own identity and state. Multiple names can alias the same object, so a mutation through one name is visible through all of them — including across a function call, where a parameter binding can refer to the caller's object. When an object is no longer reachable through any binding, it becomes eligible for reclamation according to the runtime's memory-management rules.

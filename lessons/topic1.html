Every program you write is written in some language. But why does that language look the way it does? And why are there so many different languages in the first place?

That's where we start. We'll look at programming-language paradigms, how languages can be classified and evaluated, compilation and interpretation, and the basic stages a program goes through before it runs.

  • distinguish syntax from semantics;

  • distinguish major programming paradigms;
  • classify programming languages using different criteria;
  • explain basic differences between compilation and interpretation;
  • describe the major stages of program translation; and
  • identify lexical, syntax, and semantic errors.

What Is a Programming Language?

A programming language gives us a formal way to describe computation. It tells us what we can write, how those pieces can be put together, and what those constructions mean when the program runs.

PROGRAMMING LANGUAGE
↓
SYNTAX

What is valid

SEMANTICS

What it means

EXECUTION

What happens

Syntax tells us whether a program is structurally valid. Semantics tells us what a valid program means. Execution is one way that meaning gets carried out — it isn't a third ingredient alongside syntax and semantics. Keep that distinction in mind; it will matter when we get to interpreters.

A worked example

total = price * quantity
SyntaxThe statement follows Python's syntactic rules. It contains an identifier (total), an assignment operator (=), and an expression (price * quantity).
SemanticsThe statement means: evaluate price * quantity and bind the resulting value to total.
ExecutionWhen Python executes the statement, the expression is evaluated and the resulting value becomes associated with total.

One Computation, Many Languages

Let's take the same simple computation — printing "Hello, World!" — and write it in four different languages.

Assembly

Low-level, explicit interaction with machine-oriented operations.

mov ah, 9
mov dx, offset msg
int 21h

Java

Object-oriented and strongly structured.

public class Hello {
  public static void main(String[] a) {
    System.out.println("Hello, World!");
  }
}

Scheme

Functional style.

(define (hello)
  (display "Hello, World!"))

Python

Compact, high-level syntax.

print("Hello, World!")

The computation hasn't changed. What changed is how we chose to express it. That's the interesting part: programming languages make different choices about syntax, abstraction, computation, and how programs are organized.

Think about it
What does this tell us about programming languages?
No single language is the "natural" way to express a computation — each one embodies a different set of design decisions about what to make explicit, what to abstract away, and what model of computation to build around. Understanding a language means understanding those decisions, not just memorizing its syntax.

Why Are There So Many Programming Languages?

So why not just have one language that does everything? Because language design involves competing goals:

  • readability
  • writability
  • reliability
  • performance
  • abstraction
  • safety
  • programmer productivity
  • application domain
Programming-language design involves trade-offs.

A language might give you more direct control over memory and hardware, which can be useful for performance — but that control also gives you more ways to make mistakes. Another language might give you more abstraction and automatic memory management. That can make development easier, but you give up some direct control in return.

Think about it
Why might a language designer deliberately give programmers less control?
Less direct control usually means fewer opportunities to make certain classes of mistakes — a language that manages memory automatically, for instance, removes an entire category of bugs (dangling pointers, memory leaks) that a lower-level language leaves entirely up to the programmer. The designer is trading raw control for safety and productivity, on the bet that most programmers benefit more from that trade than they lose.

What Is a Programming Paradigm?

A programming paradigm is a way of organizing and expressing computation. It influences how you approach a problem and how you structure the program — not just what syntax you type.

Paradigms are usually grouped into a few broad families:

  • Imperative — describe a sequence of steps that change program state
  • Object-oriented — organize programs around objects that bundle state and behavior
  • Functional — express computation primarily through functions and minimize reliance on changing program state
  • Logic — express facts and rules, and let the language derive conclusions
  • Declarative — describe what result is wanted, rather than the steps to get there

These categories aren't mutually exclusive. A single language, including Python, can support several paradigms. Let's start with two broad ways of thinking about computation: imperative and declarative.

Page 5

Imperative Programming

Imperative programming emphasizes how a computation is performed — a program describes a sequence of actions that changes program state.

total = 0
for x in numbers:
    total = total + x

Tracing it conceptually, step by step:

total = 0
x = first value  →  total changes
x = second value  →  total changes
x = third value  →  total changes
…

Notice what the code is doing: it spells out the operations and the changes to total, one step at a time. That's the key idea behind imperative programming — the program describes how the computation is carried out.

Check your understanding
Which programming style is most evident in the code above?
Logic programming expresses facts and rules and lets the language derive conclusions — nothing here does that; every step is spelled out directly.
Functional style avoids changing state and expresses computation as function evaluation — but this code repeatedly reassigns total, which is exactly the state-changing pattern functional style avoids.
Correct. The code is an explicit sequence of steps that changes total's state on each iteration — the defining trait of imperative programming.
Declarative code describes the result you want, not the steps to get there. This code does the opposite — it spells out every step.
Page 6

Declarative Programming

Declarative programming emphasizes what result or relationship we want, rather than spelling out every step. SQL is a familiar example:

SELECT name
FROM students
WHERE grade >= 1.5;

You don't tell the database exactly how to scan the table, compare each row, and move through the data. You describe what data you want, and the database decides how to get it.

Imperative"What steps should be performed?"
Declarative"What result do I want?"

This is a useful distinction, not an absolute rule — plenty of real code mixes both styles, sometimes in the same function.

Page 7

Python as a Multi-Paradigm Language

Consider two ways of summing a list in Python:

total = 0
for x in numbers:
    total += x

versus:

total = sum(numbers)

Both are Python programs, and both compute the sum. The first explicitly describes the iteration and state updates. The second uses a higher-level abstraction: the iteration is still happening, but sum() handles it internally rather than asking you to write it out.

Abstraction allows programmers to express computations without specifying every implementation detail.

It might be tempting to call the second version "declarative," but that isn't quite right. It's still telling Python what to do; it's just doing so at a higher level. Abstraction and paradigm are related, but they're not the same thing.

Explicit mechanism

iterate → accumulate → update

Higher-level abstraction

sum(numbers)

Now consider a third style:

top_students = list(
    filter(lambda s: s["grade"] <= 1.5, students)
)

This leans on functions as values — passing lambda into filter — which is closer to a functional style.

A programming language can support multiple paradigms. A single program can also mix multiple paradigms.

Evaluating Programming Languages

  • Readability — how easily can humans understand programs written in the language?
  • Writability — how easily can programmers express solutions?
  • Reliability — how likely is the language to help programmers produce programs that behave correctly?
  • Cost — what does it cost to learn, develop, execute, maintain, and support programs written in the language?

Imagine two languages that can both express the same algorithm. Write it in the one that spells out every operation explicitly, and you get more control but lower writability. Write it in the one that expresses the same operation in a single concise statement, and you gain writability and readability — at the cost of hiding implementation details.

There is no universally best language. Evaluation depends on the goals and context.
Think about it
Is the most writable language necessarily the best language?
No. Giving programmers many different ways to express the same operation may make a language powerful — but also harder to learn, read, and maintain. Increasing writability can come at the cost of readability, which is exactly why "best" only makes sense relative to a goal, not as an absolute property of a language.

Errors Have a Location

LexicalThe input cannot be divided into valid tokens.
SyntaxThe tokens do not form a valid program structure.
SemanticThe structure is valid, but the program violates a rule about meaning or execution.

Before you reveal the answer, try to identify where in the process the problem occurs.

Example 1
x = 10 @ 5 — in a language where @ is not a valid operator, what kind of problem is this?
Correct. @ can't even be turned into a valid token in this language — the problem happens before structure or meaning are ever considered.
Not quite — a syntax error means the tokens exist but are arranged incorrectly. Here, @ can't become a valid token at all, which is a step earlier.
Not quite — semantic errors happen when valid structure has invalid meaning. This never gets that far, since @ isn't a valid token in the first place.
Example 2
if x > 10
print(x) — what kind of problem is this?
Not quite — every character here forms a valid token (if, x, >, 10, print, and so on). The tokens themselves aren't the problem.
Correct. The tokens are all valid, but they're not arranged the way the grammar requires — this language expects a colon and an indented block after if x > 10.
Not quite — semantic errors assume the structure is already valid. This example's structure itself is the problem.
Example 3
x = "hello"
y = x + 5 — what kind of problem is this?
Not quite — every token here is valid: identifiers, an assignment operator, a string literal, a plus operator, a number.
Not quite — x + 5 is a perfectly valid expression structurally. Addition of two things is allowed by the grammar.
Correct. The structure is fine — the grammar has no problem with "expression + expression." The issue is meaning: adding a string to a number isn't a valid operation. In Python specifically, there's no separate static analysis pass that catches this ahead of time — the incompatibility is only detected when the statement actually executes, as a TypeError.

That last example points at something worth remembering: different languages detect different classes of errors at different stages. Some catch a mismatch like this before the program ever runs; others, like Python, only discover it during execution. You'll see this distinction matter again later in the course.

Check Your Understanding

Five questions covering this lesson. Not graded — just for you to check where things stand before moving on.

1
What is the difference between syntax and semantics?
Syntax is about structure — whether a program is put together according to the language's rules. Semantics is about meaning — what a structurally valid program actually does. A program can be syntactically perfect and still be semantically wrong.
2
Which programming paradigm emphasizes explicit state changes?
Correct — imperative programming describes computation as a sequence of steps that change program state, exactly like the total += x loop from Page 5.
Functional style tends to avoid changing state, expressing computation as function evaluation instead.
Logic programming expresses facts and rules and derives conclusions from them — not a sequence of state changes.
Declarative style describes the desired result, not the steps — the opposite instinct from explicit state changes.
3
Can a language belong to more than one paradigm?
Correct — Python itself is the running example: it supports imperative loops, functional idioms like filter/lambda, and object-oriented code, often in the same program.
Not quite — Page 7 showed the same language, Python, expressing the same computation in imperative and functional styles. Languages aren't locked into one paradigm.
4
What is the difference between compilation and interpretation?
Compilation translates a program into another representation (like machine code) before it runs. Interpretation processes and executes the program directly, without a separate translation step first. Many real systems, including Python, combine ideas from both rather than being purely one or the other.
5
What distinguishes a lexical error from a syntax error?
A lexical error means the characters themselves can't be turned into valid tokens (an unrecognized symbol, for instance). A syntax error means the tokens are all individually valid, but they're arranged in a way the grammar doesn't allow. Lexical analysis happens first, so a lexical error stops things before syntax is even checked.

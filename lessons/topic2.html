Syntax & Lexical Analysis

SYNTAX

what is valid

SEMANTICS

what it means

EXECUTION

what happens

How does a programming language turn the characters you type into something it can actually work with? We'll start with the first part of that process: characters → lexemes → tokens → token stream.

Here we're focusing on tokenization. The next question — how a token stream becomes structure — belongs to Topic 3, where we'll look at parsing and formal grammars.

By the end of this topic, you should be able to

  • explain what a lexeme and a token are, and how they differ;
  • tokenize a simple line of code by hand;
  • explain why a parser works with tokens rather than raw characters;
  • distinguish identifiers from keywords;
  • recognize common token categories: literals, operators, delimiters;
  • distinguish a lexical error from a syntax error; and
  • explain the difference between what lexical analysis and syntax analysis each ask.

Estimated study time: 60–90 minutes.

What Is Syntax?

Let's connect this back to Topic 1:

Valid

x = 10 + 5

Invalid

x = + 10 5
Syntax: the rules that determine how the elements of a programming language may be arranged to form valid programs.

Programming languages have formal rules for syntax, and we'll see how those rules are represented with grammars in Topic 3. For now, we're staying one step earlier: before we can check syntax, we need to turn the raw characters into the pieces that syntax rules operate on.

Characters, Lexemes, and Tokens

result = oldsum - value / 100

There are three useful levels of description here:

CharacterA single symbol in the source text — r, e, s, u, l, t, =, and so on.
LexemeA sequence of characters recognized as a lexical unit by the language — result, =, oldsum, -, value, /, 100.
TokenThe category assigned to a lexeme — IDENTIFIER, ASSIGN, IDENTIFIER, MINUS, IDENTIFIER, DIVIDE, INTEGER_LITERAL.

Why Do We Need Tokens?

total = price * quantity

The parser works with tokens rather than individual source characters. It doesn't need to inspect every character in total; it needs to know that this is an identifier and, when necessary, retain its value:

IDENTIFIERASSIGNIDENTIFIERMULTIPLYIDENTIFIER

Lexical analysis turns the raw character sequence into a more useful representation. At this point, we care about what kind of thing each piece is, not just the characters themselves.

The lexer does not yet determine the complete structure of the program. It identifies the pieces from which that structure can be built.
Page 5

What Does a Lexer Actually Do?

So what does a lexer actually do? A lexer, or scanner:

  1. reads source characters;
  2. groups characters into lexemes;
  3. identifies the token type;
  4. usually records useful information, such as the lexeme's actual value; and
  5. produces a sequence of tokens.

For example, count = 42 becomes something conceptually like:

IDENTIFIER("count")
ASSIGN
INTEGER(42)

A token can carry both a token type and an associated value (or lexeme) — INTEGER_LITERAL(42), IDENTIFIER("count"). The type tells later stages what kind of thing it is; the value preserves the actual information needed later.

You'll need that value once you're evaluating expressions rather than just recognizing them — Topic 4 leans on exactly this.

What About Whitespace?

x=10+20
x = 10 + 20

In many languages, whitespace mainly separates lexemes and is discarded or ignored by the lexer. It doesn't necessarily become a token itself, which is why these two lines can produce essentially the same token sequence.

Not always. Some languages give whitespace a syntactic role. Python, for example, uses indentation as part of its syntax. We won't get into Python's indentation handling here; just keep it in mind as an important exception.

Identifiers and Keywords

And why is if different?

IdentifiersNames defined by the language's rules for naming program entities — a programmer chooses them.
KeywordsReserved words with predefined syntactic roles — the language reserves them. In Python: if, else, while, for, def, return, class, and others.
Check your understanding
Could a Python program use return as an ordinary variable name?
Not quite — keyword status doesn't depend on context like that. return is reserved everywhere in Python, function or not.
Correct. return has a predefined syntactic role in Python — the lexer always tokenizes it as the RETURN keyword, never as an IDENTIFIER, so it can't double as a variable name.
Not quite — Python reserves a specific set of keywords precisely so they can't be reused as identifiers. return is one of them.

How Does a Lexer Recognize a Pattern?

By now you've seen the result of tokenization. But how does the lexer actually decide that total is an IDENTIFIER and 42 is an INTEGER_LITERAL? It isn't guessing. Each token type has a pattern, and the lexer checks the source characters against those patterns.

Many token patterns can be described with regular expressions — the same kind of pattern matching you can use with Python's re module:

import re
re.match(r'[A-Za-z_][A-Za-z0-9_]*', 'total')   # matches — looks like an identifier
re.match(r'[0-9]+', '42')                       # matches — looks like an integer literal

A set of strings that can be described by a regular expression is called a regular language. The token patterns we've seen so far — identifiers, integers, and similar categories — can be described this way. That's why regular expressions are useful for recognizing them.

So how does that pattern matching happen mechanically? A lexer can be modeled as a finite automaton: a machine with a fixed number of states that reads one character at a time and changes state based on what it sees. For an identifier, the idea is roughly:

start
→ sees a letter or _ → move to in an identifier
→ sees a letter, digit, or _ → stay in in an identifier
→ sees anything else → stop, emit IDENTIFIER

What if the input ends, or the machine reaches a character it can't use to continue the pattern, and it isn't in an accepting state? Then the lexer can't form a valid token from that input. That's the idea behind the lexical error on the next page.

Check your understanding
Which of these would a lexer's regular-expression patterns struggle to handle on their own, no matter how the pattern is written?
Not quite — this is exactly the kind of fixed pattern regular expressions handle well: match the literal characters i, f.
Correct — checking that parentheses balance at arbitrary depth means counting how deep you are, and a finite automaton has no memory of "how deep." That needs the grammars coming up in Topic 3.
Not quite — a fixed, non-nesting pattern like this is a standard regular expression, no counting involved.

Lexical Errors

Suppose ? isn't a valid symbol in our language:

x = 10 ? 5

The lexer encounters a character it can't classify as a valid token. That's a lexical error. The problem happens before we even get to structure.

Now compare that with this:

x = 10 + * 5

Every symbol here is recognizable as a token:

IDENTIFIERASSIGNINTEGERPLUSMULTIPLYINTEGER

The problem is not lexical. All the tokens exist; the problem is how they are arranged. That's a syntax problem.

Page 13

Syntax Errors

if x > 10
print(x)

The lexer can happily identify every token here:

IFIDENTIFIERGREATER_THANINTEGERIDENTIFIER…

In Python, the lexer can identify these tokens, but the sequence doesn't satisfy Python's syntax rules. The if statement needs a colon followed by an indented suite.

Lexical analysis asks: "What are these pieces?" Syntax analysis asks: "Can these pieces be arranged this way?"

Topic 3 examines how syntax can be described formally, and how a parser actually analyzes a token sequence to answer that second question.

Check Your Understanding

Six questions to check whether the main ideas from this topic have stuck. This isn't graded.

1
What is a lexeme?
A lexeme is a sequence of characters from the source text recognized as a lexical unit by the language — for example, total, =, or 42. A token is the category assigned to a lexeme (like IDENTIFIER or INTEGER_LITERAL); the lexeme is the actual text, the token is what kind of thing it is.
2
What is the token corresponding to 123?
Not quite — identifiers are names a programmer chooses, like variable names. 123 is a number, not a name.
Correct — 123 is a literal integer value.
Not quite — keywords are reserved words like if or while, not numbers.
3
What does a lexer produce?
A sequence of tokens — a token stream — built by reading the source character by character, grouping characters into lexemes, and assigning each lexeme a token type (often along with its actual value).
4
x = 10 + * 5 — is the problem lexical or syntactic?
Not quite — every character here forms a perfectly valid token: identifier, assign, integer, plus, multiply, integer. The tokens themselves aren't the problem.
Correct. All the tokens are individually valid — the problem is that two operators (+ and *) appear back to back with nothing between them, which the grammar doesn't allow.
5
Given x = 10 ? 5, in a language where ? is not a valid symbol, what stage detects the problem?
Lexical analysis. The character ? can't be classified as any valid token in this language, so the problem is caught before syntax or meaning are ever considered.
6
Given total = price * quantity, identify the lexemes and their token types.
total → IDENTIFIER, = → ASSIGN, price → IDENTIFIER, * → MULTIPLY, quantity → IDENTIFIER.

The Big Picture

Lexical analysis identifies the pieces. Syntax analysis determines how those pieces fit together. That's the core distinction to carry forward — along with the difference between a lexical error and a syntax error.

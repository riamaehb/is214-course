IS 214 · TOPIC 6 · STUDY GUIDE

Names, Binding, Scope & Environments

SYNTAX

what is valid

SEMANTICS

what it means

EXECUTION

what happens

Topic 5 established: value → type → valid operation. This topic asks the next question: when a program uses a name, how does the language know which value that name refers to, and where is that binding valid?

Names, bindings, scope, and environments are parts of one coherent mechanism — this lesson builds that mechanism piece by piece, ending with closures as a natural consequence of it, not a separate mysterious feature.

By the end of this topic, you should be able to

  • explain the difference between a name, a binding, and a value;
  • explain what scope is, and distinguish lexical from dynamic scope;
  • explain what an environment is, and how nested environments implement nested scope;
  • trace name lookup through a chain of nested environments;
  • implement a small nested-environment lookup function; and
  • explain why a closure retains access to its enclosing environment.

Estimated study time: 75–100 minutes.

Page 1

A Name Is Not a Value

x = 10
What is x?

It's tempting to say "x is 10." But look closer:

xa name
10a value
x = 10
y = x
  • Are x and y the same name? No — two different names.
  • Do they refer to the same value? Yes, right now — both refer to 10.
  • What happens if x changes later? We'll find out on the next page — but notice you can't yet answer this from the code alone.
Names, bindings, and values are related, but they are not the same thing.
Page 2

Names, Bindings, and Rebinding

A binding establishes an association between a name and a value.

More precisely, a binding associates a name with a value or object — we'll look closely at what that distinction means, and at references, identity, aliasing, and mutability, in Topic 9. For now, "value" is close enough.

x = 10
x ─────→ 10
x = 20
x ─────→ 20

Assignment establishes or updates a binding — it doesn't make a name permanently "contain" a value. The emphasis is on the relationship between the name and whatever it currently refers to.

Predict
Trace this: x = 10, then y = x, then x = 20. What does y refer to now?
y still refers to the same value that x referred to at that moment — 10. y = x made y refer to whatever x referred to right then; it didn't create a permanent link between the two names, and it didn't copy anything into a separate slot for y. Rebinding x afterward has no effect on y, since y's own binding was already settled.
Page 3

Names Have Context

x = 10

def f():
    x = 20
When f() runs, which x is being used?

There are now two different bindings for the name x — one outside f, one inside it. Nothing we've defined so far tells us which one a given piece of code actually sees.

That gap is exactly what scope is about to answer.

Page 4

Scope: Local and Global

Scope is the region of a program in which a binding is visible or can be referenced.
x = 10

def f():
    y = 20
    print(x)
    print(y)
  • Can f() access x? Yes — x is visible from inside f.
  • Can the outside program access y? No — y only exists within f's scope.
Global scopex
Local (function) scopey

Scope isn't a vocabulary word to memorize — it's the answer to a real question a program forces you to ask: from right here, what names can I actually see?

inner() can see all three: its own z, outer's y, and the global x. This is lexical scope: name visibility is determined by where code is written, not by how it happens to be called.

This is the scoping model you'll use for the rest of the course.

Page 6

Dynamic Scope

A useful contrast, not something you'll implement:

x = "global"

def f():
    print(x)

def g():
    x = "local"
    f()
Lexical scopef finds the global x — because that's where f was written.
Dynamic scopef would find g's x instead — because that's who called it.
Lexical scope follows program structure. Dynamic scope follows the calling context.

Python uses lexical scope. Dynamic scope is here for comparison — to understand it as a real language-design choice other languages have made, not something you need to build.

Page 7

Scope vs. Lifetime

ScopeWhere a binding is visible.
LifetimeHow long the associated value or runtime entity exists.
def f():
    y = 20
    return y

y's scope is the body of f — that's where the name is visible. Its lifetime is about how long the associated runtime entity remains available. These are genuinely different questions: scope is about visibility, while lifetime is about duration.

That's not the whole story, though — closures provide an important case where a binding from an enclosing function remains reachable well after that function has returned. We'll see exactly how in a few pages.

We're not going into memory-management details here — that's Topic 9.

Start with a flat environment:

    "bindings": {"x": 10, "y": 20},

Then extend your function to handle nested environments:

environment = {
    "bindings": {"y": 20},
    "parent": {
        "bindings": {"x": 10},

}

Expected behavior:

lookup("y", environment)  # 20
lookup("x", environment)  # 10
lookup("z", environment)  # undefined-name error
Specify exactly how a failed lookup is represented — for example, raise a NameError. A failed lookup must be clearly distinguishable from a legitimate value like None.

This small function is a working model of the environment structure your own interpreter will eventually need.

Page 12

Lookup vs. Assignment

Lookupx asks: what value is currently associated with x?
Assignmentx = 10 asks: establish or update the binding for x.

Trace the environment after each statement:

x = 10
y = x
x = 20
Trace it
What does the environment look like after each of the three lines?
After x = 10: x → 10. After y = x: x → 10, y → 10 — y looked up x's current value and bound itself to it. After x = 20: x → 20, y → 10 — only x's binding changed; y was never linked to x itself, only to the value x had at the moment of the lookup.

Deeper questions about references and aliasing — what happens with mutable objects specifically — wait until Topic 9. For now, this is purely about binding and lookup.

Page 13

Closures

def make_adder(x):
    def add(y):
        return x + y
    return add

add5 = make_adder(5)
add5(3)
make_adder has already finished running. Where does add get x from?
  1. make_adder(5) creates a binding x → 5.
  2. add is defined inside that environment.
  3. add is returned.
  4. The call to make_adder finishes.
  5. The binding x → 5 remains available — captured by add.
  6. add5(3) looks up x through that captured environment.
  7. The result is 8.

Page 14

Synthesis: Trace the Environment

The main reasoning challenge of this topic:

x = 10

def outer():
    x = 20
    def inner():
        return x
    return inner

f = outer()
print(f())

Trace through: the global x, the outer call, the local x inside outer, the inner function, the environment inner captures, what happens when f() is called, and which x lookup actually finds.

Trace it
What does print(f()) output?
20. outer() creates its own local x → 20, shadowing the global one. inner is defined inside outer's environment, so it captures that environment — the one where x is 20 — not the global one. outer() returns inner (bound to f), and even though outer has already finished running by the time f() is called, the captured environment is still there. Lookup finds outer's x first, before it would ever reach the global one.
Page 15

Check Your Understanding

Eight questions that ask you to apply this topic's ideas. Not graded — just for you to check where things stand before moving on.

1 · Name vs. value
In count = 0, what are the two separate things involved, and how do they relate to each other?
count is a name; 0 is a value. The statement doesn't make count "contain" 0 — it establishes a binding between them, a relationship that assignment can later update to point count at a different value entirely.
2 · Binding
What actually happens, in terms of bindings, when x = 10 executes?
A binding is established — an association between the name x and the value 10 is recorded, so that later references to x can find that value again. Nothing is "stored inside" x; the binding is the relationship itself.
3 · Rebinding
Given a = 5, then b = a, then a = 99 — what does b refer to, and why doesn't changing a affect it?
b still refers to 5. b = a bound b to whatever value a held at that moment — not to a itself. Rebinding a afterward only changes what a refers to; b's binding was already settled.
4 · Scope
A function reassigns a variable that shares a name with a global variable. Does the global change? What determines the answer?
Not necessarily — it depends on scope. If the assignment inside the function creates a new local binding (Python's normal behavior), the global is untouched; the function's local x and the global x are simply two different bindings that happen to share a name.
5 · Lexical vs. dynamic scope
f is defined at the top level and references a global x. g defines its own local x and then calls f. Under lexical scope, which x does f use? What would dynamic scope say instead?
Under lexical scope, f uses the global x — because that's where f was written, and lexical scope only cares about program structure, never about who's calling. Under dynamic scope, the lookup would instead follow the calling context and find g's local x — since f is running because g called it. Python uses lexical scope, so the first answer is what actually happens.
6 · Environment
Why does an interpreter need an environment at all — why not just search the program text for the most recent assignment to a name?
Because "most recent" isn't well-defined at runtime — the same line of code can run many times (different function calls, recursive calls, closures) each with its own bindings. An environment gives the interpreter an actual runtime structure — name-to-value associations that exist independently of the source text — so lookup has something concrete to search instead of trying to reconstruct history from the code itself.
7 · Nested lookup
Given the nested environment {bindings: {y: 1}, parent: {bindings: {x: 2}, parent: None}}, trace lookup("x") step by step.
Check the current environment's bindings — x isn't there, only y. Follow the parent pointer to the enclosing environment. Check its bindings — x → 2 is found. Return 2.
8 · Closures
make_adder has already returned by the time add5(3) runs. Why does add5 still know what x is?
Because add retains access to the environment it was defined in — the one containing x → 5 — for as long as add itself exists. The environment remains reachable specifically because the returned function keeps a reference to it, which is exactly what makes it a closure.
Final synthesis

If Topic 5 tells us what kind of value we have, what does Topic 6 tell us?

Which value a name refers to, where that binding is visible, and how the runtime actually finds it.

Names, Binding, Scope & Environments

SYNTAX

what is valid

SEMANTICS

what it means

EXECUTION

what happens

Topic 5 established value → type → valid operation. Now we can ask the next question: when a program uses a name, how does the language know which value that name refers to, and where is that binding valid?

Names, bindings, scope, and environments are really parts of one mechanism. We'll build that mechanism piece by piece, and closures will come out of it naturally rather than appearing as a separate mysterious feature.

By the end of this topic, you should be able to

  • explain the difference between a name, a binding, and a value;
  • explain what scope is, and distinguish lexical from dynamic scope;
  • explain what an environment is, and how nested environments implement nested scope;
  • trace name lookup through a chain of nested environments;
  • implement a small nested-environment lookup function; and
  • explain why a closure retains access to its enclosing environment.

Estimated study time: 75–100 minutes.

Page 1

A Name Is Not a Value

x = 10
What is x?

It's tempting to say "x is 10." But let's slow down and look at what's actually here:

xa name
10a value
x = 10
y = x
  • Are x and y the same name? No — they're two different names.
  • Do they refer to the same value? Yes, right now — both refer to 10.
  • What happens if x changes later? We'll get to that next. For now, notice that you can't answer it by treating x as if it simply "contains" 10.
Names, bindings, and values are related, but they are not the same thing.
Page 2

Names, Bindings, and Rebinding

A binding establishes an association between a name and a value.

More precisely, a binding associates a name with a value or object. We'll look more closely at references, identity, aliasing, and mutability in Topic 9. For now, "value" is enough for the model we're building.

x = 10
x ─────→ 10
x = 20
x ─────→ 20

Assignment establishes or updates a binding. It doesn't make a name permanently "contain" a value. The important thing is the relationship between the name and whatever it currently refers to.

Predict
Trace this: x = 10, then y = x, then x = 20. What does y refer to now?
y still refers to 10. At the moment y = x runs, the interpreter looks up x and uses that value to establish y's own binding. Rebinding x afterward doesn't change y.
Page 3

Names Have Context

x = 10

def f():
    x = 20
When f() runs, which x is being used?

There are now two bindings for the name x — one outside f, one inside it. But which one does a particular piece of code actually see? We need another concept to answer that.

That is exactly what scope is about.

Page 4

Scope: Local and Global

Scope is about visibility. Lifetime is about duration.
x = 10

def f():
    y = 20
    print(x)
    print(y)
  • Can f() access x? Yes — x is visible from inside f.
  • Can the outside program access y? No — y only exists within f's scope.
Global scopex
Local (function) scopey

Scope isn't just a vocabulary word to memorize. It's the answer to a question the program forces us to ask: from right here, what names can I actually see?

This is the scoping model we'll use for the rest of the course.

Page 6

Dynamic Scope

Here's a useful contrast. You won't implement this one:

x = "global"

def f():
    print(x)

def g():
    x = "local"
    f()
Lexical scopef finds the global x — because that's where f was written.
Dynamic scopef would find g's x instead — because that's who called it.
Lexical scope follows program structure. Dynamic scope follows the calling context.

Python uses lexical scope. Dynamic scope is here for comparison — it's a real language-design choice, but not something you'll implement.

Page 7

Scope vs. Lifetime

ScopeWhere a binding is visible.
LifetimeHow long the associated value or runtime entity exists.
def f():
    y = 20
    return y

y's scope is the body of f — that's where the name is visible. Its lifetime is about how long the associated runtime entity remains available. These are genuinely different questions: scope is about visibility, while lifetime is about duration.

That's not the whole story, though. Closures give us an important case where a binding from an enclosing function remains reachable after that function has returned. We'll see exactly how in a few pages.

We're not going into memory-management details here — that's Topic 9.

Build: Implement Name Lookup

Let's start with a flat environment:

def lookup(name, environment):
    ...

environment = {
    "bindings": {"x": 10, "y": 20},
    "parent": None
}

Then extend the function so it can follow parent environments:

environment = {
    "bindings": {"y": 20},
    "parent": {
        "bindings": {"x": 10},
        "parent": None
    }
}

Expected behavior:

lookup("y", environment)  # 20
lookup("x", environment)  # 10
lookup("z", environment)  # undefined-name error
Be explicit about what happens when lookup fails — for example, raise a NameError. A failed lookup must be distinguishable from a legitimate value such as None.

This small function is a working model of the environment structure your interpreter will eventually need.

Page 12

Lookup vs. Assignment

Lookupx asks: what value is currently associated with x?
Assignmentx = 10 asks: establish or update the binding for x.

Let's trace the environment after each statement:

x = 10
y = x
x = 20
Trace it
What does the environment look like after each of the three lines?
After x = 10: x → 10. After y = x: x → 10, y → 10. Then after x = 20: x → 20, y → 10. The important part is that rebinding x changes x's binding; it doesn't reach over and change y's binding.

We'll wait until Topic 9 for the deeper questions about references and aliasing, especially with mutable objects. For now, we're focusing on binding and lookup.

Page 13

Closures

def make_adder(x):
    def add(y):
        return x + y
    return add

add5 = make_adder(5)
add5(3)
make_adder has already finished running. So where does add get x from?
  1. make_adder(5) creates a binding x → 5.
  2. add is defined inside that environment.
  3. add is returned.
  4. The call to make_adder finishes.
  5. The binding x → 5 remains available — captured by add.
  6. add5(3) looks up x through that captured environment.
  7. The result is 8.

Page 14

Synthesis: Trace the Environment

Here's the main tracing challenge from this topic:

x = 10

def outer():
    x = 20
    def inner():
        return x
    return inner

f = outer()
print(f())

Trace the global x, the outer call, the local x inside outer, the inner function, the environment inner captures, and finally which x the lookup finds when f() runs.

Trace it
What does print(f()) output?
20. outer() creates its own local x → 20, which shadows the global x. Because inner is defined inside outer, it captures that enclosing environment. When f() is later called, lookup finds the captured x → 20 before it would ever reach the global environment.
Page 15

Check Your Understanding

Eight questions to check whether you can apply the ideas from this topic. This isn't graded.

1 · Name vs. value
In count = 0, what are the two separate things involved, and how do they relate to each other?
count is a name; 0 is a value. The statement doesn't make count "contain" 0 — it establishes a binding between them, a relationship that assignment can later update to point count at a different value entirely.
2 · Binding
What actually happens, in terms of bindings, when x = 10 executes?
A binding is established between the name x and the value 10, so later references to x can find that value. The important idea is the binding itself: x is a name, not a container holding 10.
3 · Rebinding
Given a = 5, then b = a, then a = 99 — what does b refer to, and why doesn't changing a affect it?
b still refers to 5. b = a bound b to whatever value a held at that moment — not to a itself. Rebinding a afterward only changes what a refers to; b's binding was already settled.
4 · Scope
A function reassigns a variable that shares a name with a global variable. Does the global change? What determines the answer?
Not necessarily — it depends on scope. If the assignment inside the function creates a new local binding (Python's normal behavior), the global is untouched; the function's local x and the global x are simply two different bindings that happen to share a name.
5 · Lexical vs. dynamic scope
f is defined at the top level and references a global x. g defines its own local x and then calls f. Under lexical scope, which x does f use? What would dynamic scope say instead?
Under lexical scope, f uses the global x — because that's where f was written, and lexical scope only cares about program structure, never about who's calling. Under dynamic scope, the lookup would instead follow the calling context and find g's local x — since f is running because g called it. Python uses lexical scope, so the first answer is what actually happens.
6 · Environment
Why does an interpreter need an environment at all — why not just search the program text for the most recent assignment to a name?
Because "most recent" isn't enough to describe runtime state. The same line of code can run many times — in different function calls, recursive calls, or closures — with different bindings each time. An environment gives the interpreter an actual runtime structure to search, instead of trying to reconstruct runtime state from the source text.
7 · Nested lookup
Given the nested environment {bindings: {y: 1}, parent: {bindings: {x: 2}, parent: None}}, trace lookup("x") step by step.
First check the current environment: x isn't there; only y is. Follow the parent pointer. In the enclosing environment, x → 2 is found. Return 2.
8 · Closures
make_adder has already returned by the time add5(3) runs. Why does add5 still know what x is?
Because add retains access to the environment in which it was defined — the one containing x → 5. The returned function keeps that environment reachable, which is exactly what makes add a closure.
Final synthesis

If Topic 5 tells us what kind of value we have, what does Topic 6 tell us?

Which value a name refers to, where that binding is visible, and how the runtime actually finds it.

This topic follows one expression, x = a + b * c, through every one of these stages. By the end, all of these ideas — grammar, derivation, parse tree, AST, parser — should feel like different views of the same thing, not a pile of separate vocabulary.

By the end of this topic, you should be able to

  • explain what a grammar is and read BNF-style production rules;
  • derive a sentence from a grammar, step by step;
  • construct and interpret parse trees;
  • explain what makes a grammar ambiguous, and why that's a problem;
  • explain how grammar structure encodes precedence and associativity;
  • distinguish a parse tree from an abstract syntax tree (AST);
  • explain what parsing is, and the difference between top-down and bottom-up approaches; and
  • explain how a grammar can directly guide the structure of a recursive-descent parser.

From Tokens to Structure

Topic 2 left us with a token stream. For x = a + b * c:

IDENTIFIERASSIGNIDENTIFIERPLUSIDENTIFIERMULTIPLYIDENTIFIER

We know what each piece is. But how do we know how these pieces are related? We need to know that this means x gets assigned the result of adding a to the product of b and c — not some other arrangement.

That's the motivation for this entire topic: syntax analysis, or parsing — detecting whether a token sequence is valid, and constructing the structure it represents.

Page 2

What Is a Grammar?

A grammar is a set of rules that describes how valid programs can be constructed.

Just like Topic 2's tokens gave the parser something more useful than raw characters, a grammar gives us something more precise than "arrange the tokens so it looks right." It's a formal, checkable definition of structure.

We'll build one up slowly, a few pieces at a time — not throw a giant grammar at you all at once.

Page 4

Reading Production Rules

Let's read one carefully:

<expr> ::= <term> + <term>
  • <expr> is a non-terminal;
  • ::= means "can be defined as";
  • <term> is another non-terminal;
  • + is a terminal;
  • the right-hand side describes one possible form of an <expr>.
<expr> ::= <term>
       | <term> + <term>

The | introduces an alternative — an <expr> can take either form.

Check your understanding
In <expr> ::= <id> | <id> + <id>, what is <id>?
Not quite — terminals are actual symbols like a or +. <id> is a placeholder category that expands into one of those.
Correct — it's written in angle brackets, and it's defined by its own production rule elsewhere in the grammar.
Not quite — in this grammar, <assignment> is where derivations begin, not <id>.
Page 5

A Small Programming Language

Let's build a grammar that can generate our running example, x = a + b * c:

<assignment> ::= <id> = <expr>
<expr>       ::= <expr> + <expr>
             | <expr> * <expr>
             | <id>
<id>         ::= a | b | c | x

This is enough to generate assignments involving addition and multiplication of our four identifiers. We'll use exactly this grammar for the next several pages.

It looks complete — but it has a hidden problem we'll discover in a few pages.

Page 6

Derivations

A derivation is a sequence of steps, starting from the start symbol, where at each step one non-terminal is replaced by the right-hand side of one of its productions — the same idea from Topic 2's grammar preview, now with a grammar big enough to be genuinely useful.

A derivation proves a string belongs to the language the grammar defines: step by step, from <assignment> down to actual characters.

Page 7

A Worked Derivation

Let's derive x = a + b * c, one step at a time.

<assignment>
⇒ <id> = <expr>
⇒ x = <expr>
Next step
We're at x = <expr>. To eventually reach x = a + b * c, which production do we apply to <expr> first?
Correct — since we're trying to derive this particular target string, we choose the + production here. Notice, though, that the grammar itself doesn't yet tell us + has to be the outermost operation — nothing stops us from choosing * first instead. That's the ambiguity we'll uncover shortly.
This would put multiplication at the outermost level, giving us something like (a + b) * c once fully expanded — not what we're deriving right now, though this grammar would actually allow it too.
This would give just x = a (or another single identifier) — no operators at all, so we'd never reach a + b * c.
x = <expr>
⇒ x = <expr> + <expr>
⇒ x = a + <expr>
⇒ x = a + <expr> * <expr>
⇒ x = a + b * <expr>
⇒ x = a + b * c

We've generated a sentence belonging to the language defined by the grammar — proof, step by step, that x = a + b * c is valid.

Page 8

Parse Trees

The same derivation, shown as structure instead of steps:

<assignment>
├── <id> → x
├── =
└── <expr>
    ├── <expr> → a
    ├── +
    └── <expr>
        ├── <expr> → b
        ├── *
        └── <expr> → c

The root is the start symbol. Interior nodes are non-terminals; leaves are terminals. Read the leaves left to right, and you get back x = a + b * c.

Page 9

From Derivation to Parse Tree

A derivation shows the steps used to generate a sentence. A parse tree shows the structure of the resulting sentence.

Same information, two different views — a process versus a shape. Both prove the same thing: that x = a + b * c legally belongs to the language our grammar defines.

But look closely at the tree on the last page. Is b * c really forced to group together before the addition happens — or could our grammar have built this a different way?

Page 10

Ambiguous Grammars

Here's our grammar's hidden problem. It also allows this derivation for the same expression a + b * c:

Tree 1 (what we built)

+
├── a
└── *
    ├── b
    └── c

Tree 2 (also legal!)

*
├── +
│   ├── a
│   └── b
└── c

A grammar is ambiguous if some sentence it generates has two or more genuinely different parse trees — and ours does. Nothing in the grammar itself says * should bind tighter than +; both trees are equally legal derivations of the same string.

Think about it
Why is this a problem?
Because structure determines meaning. Tree 1 computes b*c first, then adds a — the arithmetic we'd expect. Tree 2 computes a+b first, then multiplies by c — a different value entirely. A grammar isn't just supposed to recognize valid programs; it's supposed to give each one a single, intended structure. An ambiguous grammar fails at that second job.
Page 11

Operator Precedence

The fix: rewrite the grammar so addition and multiplication live at different levels.

<expr> ::= <term>   | <expr> + <term>
<term> ::= <id>     | <term> * <id>
expression
↓
term

Because multiplication is handled at the <term> level, nested one layer below <expr> where addition lives, there is now exactly one parse structure for x = a + b * c: Tree 1 from the last page, never Tree 2.

Grammar structure can encode operator precedence.

This is much more useful than just being told "multiplication has higher precedence" — you now understand how a grammar can enforce that fact by construction.

Page 12

Associativity

Precedence resolves conflicts between different operators. What about the same operator, repeated?

a - b - c

Left-associative

(a - b) - c

Right-associative

a - (b - c)

These give different results — and just like precedence, the grammar decides which one is derivable. A left-recursive rule like <expr> ::= <expr> - <term> forces left-associativity.

Precedence determines which operators bind more strongly. Associativity determines how operators of the same precedence are grouped.
Page 13

Parse Tree vs. AST

Parse TreeAbstract Syntax Tree (AST)
Represents grammar structureRepresents essential program structure
Contains many syntactic detailsRemoves unnecessary syntactic details
Closely follows grammar rulesDesigned for later processing
Useful for understanding parsingUseful for interpretation/compilation

A parse tree represents the grammar in detail — every <expr>, every <term>. An abstract syntax tree keeps only the structural information needed to understand or execute the program.

Take (x + y): a parse tree may contain explicit nodes for the parentheses themselves. An AST generally doesn't need a "parentheses" node at all — the tree's shape already captures the grouping without needing to record how it was written.

Page 14

Building an AST

Take our fixed parse tree for x = a + b * c and strip it down to what actually matters for evaluation:

Parse tree

<assignment>
├── x
├── =
└── <expr>
    ├── <term>→a
    ├── +
    └── <term>
        ├── b
        ├── *
        └── c

AST

Assignment
├── x
└── Add
    ├── a
    └── Mult
        ├── b
        └── c

Gone: the <expr>/<term> scaffolding that only existed to encode precedence, and the literal = token. What's left: exactly the information needed to evaluate the expression — an assignment, an addition, a multiplication, and the identifiers involved.

The interpreter doesn't want to evaluate a giant grammar tree full of <expr>, <term>, and <factor> nodes. It wants the AST.

This is the exact structure we'll eventually evaluate when we build the interpreter.

Page 16

Top-Down vs. Bottom-Up Parsing

Top-down

Starts from the root (the start symbol) and constructs the tree downward, toward the input tokens.

Bottom-up

Starts from the input tokens and constructs the tree upward, toward the start symbol.

Bottom-up parsers (the LR family is the best-known example) are an important part of the parsing landscape, but we won't implement one in this course — the interpreter we build uses a top-down, recursive-descent approach instead. That's what the rest of this topic is about.

Page 17

Recursive Descent

Recall our precedence-fixed grammar from Page 11:

<expr> ::= <term> | <expr> + <term>
<term> ::= <id>   | <term> * <id>

One small addition first: a <factor> level, so parentheses have somewhere to live.

<expr>   ::= <term>   | <expr> + <term>
<term>   ::= <factor> | <term> * <factor>
<factor> ::= <id>     | ( <expr> )

Recursive descent gives each non-terminal its own function, calling the functions for whatever's nested inside it:

parse_expr()
↓
parse_term()
↓
parse_factor()
The grammar can directly guide the structure of the parser.

Each production rule becomes a function. Each alternative becomes a branch inside that function. Once you see this, the whole idea of "writing a parser" stops being mysterious — you're translating a grammar you already know how to read into code.

Page 18

Building the Parser

Here's what parse_expr looks like, following our grammar directly:

def parse_expr():
    left = parse_term()
    while current_token == PLUS:
        advance()
        right = parse_term()
        left = BinaryOp('+', left, right)
    return left

Notice it builds a BinaryOp node directly — this function isn't just recognizing valid input, it's constructing an AST as it goes, without a separate parse-tree stage first. parse_term() follows the exact same shape, one level down, handling * instead of +.

Page 19

Grammar Constraints for Recursive Descent

Left recursion breaks this technique. Suppose we'd written our own <expr> rule the more "obvious" way:

<expr> ::= <expr> + <term> | <term>

A recursive-descent parse_expr() for this rule would call itself before consuming any token — infinite recursion before anything happens. That's exactly why we wrote our actual grammar with the repetition inside the rule (<expr> ::= <term> | <expr> + <term>) instead of the rule calling itself as its own first symbol.

Lookahead: when a grammar offers several alternatives, the parser needs enough information from the next token to pick the right one. If a statement can start with an assignment, an if, or a while, seeing IDENTIFIER next means "try assignment"; seeing IF means "try the if-statement." We'll go deeper into this when we actually design the interpreter's parser.

Check Your Understanding

Six questions covering this topic. Not graded — just for you to check where things stand before moving on.

1
What's the difference between a derivation and a parse tree?
A derivation is the sequence of steps used to generate a sentence from the start symbol. A parse tree is the hierarchical structure that results — the same information, shown as a shape instead of a process.
2
A grammar is ambiguous if…
Not quite — nearly every useful grammar has multiple non-terminals. That alone doesn't make it ambiguous.
Correct — that's exactly what happened with our unfixed grammar and a + b * c.
Not quite — an ambiguous grammar generates plenty of valid sentences. The problem is some of them have more than one valid structure.
3
How does grammar structure encode operator precedence?
By nesting the higher-precedence operator's rule inside the lower-precedence one — like putting multiplication at the <term> level, one layer below addition's <expr> level. That nesting forces the tighter-binding operator to be built first, with no ambiguity possible.
4
Why would an interpreter prefer an AST over a full parse tree?
A parse tree is cluttered with grammar scaffolding — nodes for <expr>, <term>, <factor>, parentheses — that only existed to make parsing unambiguous. An AST keeps just the information needed to evaluate the program: what operation, on what operands. Much simpler to walk and evaluate.
5
Which parsing approach does the recursive-descent technique from this topic follow?
Correct — recursive descent starts from the start symbol (via parse_expr(), the outermost call) and works down toward the tokens.
Not quite — bottom-up parsers start from the tokens and build upward toward the start symbol. Recursive descent goes the other direction.
6
Why does left recursion break a recursive-descent parser?
A rule like <expr> ::= <expr> + <term> would make the function for <expr> call itself immediately, before consuming any token — infinite recursion with no base case ever reached. Rewriting the repetition to sit inside the rule instead of at its start avoids the problem entirely.

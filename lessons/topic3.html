We'll use one expression, x = a + b * c, throughout this topic. The goal is for grammar, derivation, parse tree, AST, and parser to feel like different views of the same problem, rather than a pile of vocabulary to memorize.

By the end of this topic, you should be able to

  • explain what a grammar is and read BNF-style production rules;
  • derive a sentence from a grammar, step by step;
  • construct and interpret parse trees;
  • explain what makes a grammar ambiguous, and why that's a problem;
  • explain how grammar structure encodes precedence and associativity;
  • distinguish a parse tree from an abstract syntax tree (AST);
  • explain what parsing is, and the difference between top-down and bottom-up approaches; and
  • explain how a grammar can directly guide the structure of a recursive-descent parser.

Estimated study time: 75–100 minutes.

From Tokens to Structure

Topic 2 left us with a token stream. Let's use our running example again: x = a + b * c

IDENTIFIERASSIGNIDENTIFIERPLUSIDENTIFIERMULTIPLYIDENTIFIER

We know what each piece is. But we don't yet know how the pieces are related. Does this mean x gets the result of adding a to the product of b and c? Or could the tokens be grouped another way?

That's the problem this topic is about: syntax analysis, or parsing. We want to know whether a token sequence is valid and, if it is, what structure it represents.

Page 2

What Is a Grammar?

A grammar is a set of rules that describes how valid programs can be constructed.

Just as Topic 2 turned raw characters into something more useful with tokens, a grammar gives us something more precise than "arrange these tokens so they look right." It gives us a formal, checkable description of valid structure.

We'll build one up slowly, a few pieces at a time. No giant grammar dump.

Page 4

Reading Production Rules

Let's slow down and read one carefully:

<expr> ::= <term> + <term>
  • <expr> is a non-terminal;
  • ::= means "can be defined as";
  • <term> is another non-terminal;
  • + is a terminal;
  • the right-hand side describes one possible form of an <expr>.
<expr> ::= <term>
       | <term> + <term>

The | introduces an alternative: an <expr> can take either form.

Check your understanding
In <expr> ::= <id> | <id> + <id>, what is <id>?
Not quite — terminals are actual symbols like a or +. <id> is a placeholder category that expands into one of those.
Correct — it's written in angle brackets, and it's defined by its own production rule elsewhere in the grammar.
Not quite — in this grammar, <assignment> is where derivations begin, not <id>.
Page 5

Why Grammars? What Regular Expressions Can't Do

Topic 2's lexer worked because the token patterns we were recognizing don't need arbitrary nesting. Identifiers, integers, and operators are essentially flat. A regular expression can recognize those patterns, but it doesn't have a way to remember "how deep am I?"

Program structure is different. It nests:

((a + b) * (c + d))

Parentheses have to balance at whatever depth the programmer chooses. Could one fixed regular expression handle every possible depth? No. You would need to account for depth 1, depth 2, depth 3, and so on — with no fixed limit.

This is where a grammar gives us something a regular expression can't: a production rule can refer to itself.

<expr> ::= <id>
    | ( <expr> )
    | <expr> + <expr>

Notice that <expr> appears inside its own definition. That means the rule can keep expanding: one level of nesting, twenty levels, or however many the input needs. We don't need a separate rule for every possible depth.

Grammars can describe recursive structure. Regular expressions, in the sense we're using here, cannot.

Grammars with this kind of self-referencing rule are called context-free grammars (CFGs). Every grammar you'll see in this course is context-free — it's the standard tool for specifying programming-language syntax. And regular languages, from Topic 2, turn out to be a subset of what CFGs can describe: everything a regular expression can match, a grammar can too, but not the other way around.

There's one important boundary to keep in mind. A context-free grammar checks structure, not meaning. It can tell us that x = a + b * c has the shape of a valid assignment. It can't tell us whether a was ever defined, or whether adding a and b makes sense. We'll pick that up in Topic 4.

Check your understanding
Why can't a regular expression alone check that parentheses are balanced, no matter how it's written?
Not quite — regular expressions can match any fixed character, parentheses included. That's not the limitation here.
Correct — matching balanced parentheses at arbitrary depth means counting how many are still open, and a finite automaton has a fixed number of states, not a counter that can grow without bound.
Not quite — nested parentheses, nested blocks, and nested expressions are everywhere in real languages, which is exactly why this limitation matters.
Page 6

A Small Programming Language

Let's build a small grammar for our running example, x = a + b * c:

<assignment> ::= <id> = <expr>
<expr>       ::= <expr> + <expr>
             | <expr> * <expr>
             | <id>
<id>         ::= a | b | c | x

This is enough to generate assignments involving addition and multiplication of our four identifiers. We'll keep using this grammar for the next several pages.

It looks reasonable. But it has a hidden problem, and we'll find it in a few pages.

Page 7

Derivations

A derivation is a sequence of steps that starts at the start symbol. At each step, we replace one non-terminal with the right-hand side of one of its productions. It's the same basic idea we previewed earlier, now with a grammar large enough to do something useful.

A derivation gives us a step-by-step way to show that a string belongs to the language defined by the grammar — from <assignment> all the way down to actual symbols.

Page 8

A Worked Derivation

Let's derive x = a + b * c one step at a time.

<assignment>
⇒ <id> = <expr>
⇒ x = <expr>
Next step
We're at x = <expr>. To eventually reach x = a + b * c, which production do we apply to <expr> first?
Correct — since we're trying to derive this particular target string, we choose the + production here. Notice, though, that the grammar itself doesn't yet tell us + has to be the outermost operation — nothing stops us from choosing * first instead. That's the ambiguity we'll uncover shortly.
This would put multiplication at the outermost level, giving us something like (a + b) * c once fully expanded — not what we're deriving right now, though this grammar would actually allow it too.
This would give just x = a (or another single identifier) — no operators at all, so we'd never reach a + b * c.
x = <expr>
⇒ x = <expr> + <expr>
⇒ x = a + <expr>
⇒ x = a + <expr> * <expr>
⇒ x = a + b * <expr>
⇒ x = a + b * c

We've generated a sentence in the language defined by the grammar. In other words, we've shown step by step that x = a + b * c is valid according to this grammar.

Page 9

Parse Trees

Now let's look at that same derivation as a structure rather than as a sequence of steps:

<assignment>
├── <id> → x
├── =
└── <expr>
    ├── <expr> → a
    ├── +
    └── <expr>
        ├── <expr> → b
        ├── *
        └── <expr> → c

The root is the start symbol. The interior nodes are non-terminals, and the leaves are terminals. Read the leaves from left to right and you get x = a + b * c back.

Page 10

From Derivation to Parse Tree

A derivation shows the steps used to generate a sentence. A parse tree shows the structure of the resulting sentence.

Same information, two views: a derivation shows the process; a parse tree shows the resulting shape. Both tell us that x = a + b * c belongs to the language defined by the grammar.

But there's a problem hiding in that tree. Is b * c really forced to happen before the addition? Or could the grammar build a different structure for the same expression?

Page 11

Ambiguous Grammars

Here's the problem. Our grammar also allows a different structure for the same expression, a + b * c:

Tree 1 (what we built)

+
├── a
└── *
    ├── b
    └── c

Tree 2 (also legal!)

*
├── +
│   ├── a
│   └── b
└── c

A grammar is ambiguous if some sentence it generates has two or more different parse trees. Ours does. Nothing in this grammar says that * should bind more tightly than +, so both trees are legal.

Think about it
Why is this a problem?
Because structure determines meaning. Tree 1 computes b*c first, then adds a — the arithmetic we'd expect. Tree 2 computes a+b first, then multiplies by c — a different value entirely. A grammar isn't just supposed to recognize valid programs; it's supposed to give each one a single, intended structure. An ambiguous grammar fails at that second job.
Page 12

Operator Precedence

So how do we fix it? We rewrite the grammar so addition and multiplication live at different levels.

<expr> ::= <term>   | <expr> + <term>
<term> ::= <id>     | <term> * <id>
expression
↓
term

Multiplication is handled at the <term> level, one level below the <expr> level where addition lives. That structure forces b * c to form first, so x = a + b * c has exactly one parse structure here: Tree 1, not Tree 2.

Grammar structure can encode operator precedence.

This is more useful than simply memorizing that "multiplication has higher precedence." You can now see how the grammar enforces that relationship.

Page 13

Associativity

Precedence handles conflicts between different operators. What happens when the same operator appears repeatedly?

a - b - c

Left-associative

(a - b) - c

Right-associative

a - (b - c)

These group the operations differently, and they can produce different results. Just like precedence, the grammar can determine which grouping is allowed. A left-recursive rule such as <expr> ::= <expr> - <term> gives left-associative grouping.

Precedence determines which operators bind more strongly. Associativity determines how operators of the same precedence are grouped.
Page 14

Parse Tree vs. AST

Parse TreeAbstract Syntax Tree (AST)
Represents grammar structureRepresents essential program structure
Contains many syntactic detailsRemoves unnecessary syntactic details
Closely follows grammar rulesDesigned for later processing
Useful for understanding parsingUseful for interpretation/compilation

A parse tree represents the grammar in detail — including all those <expr> and <term> nodes. An abstract syntax tree, or AST, keeps the structural information that matters for later processing.

For example, take (x + y). A parse tree may represent the parentheses explicitly because they appear in the grammar. An AST generally doesn't need a separate "parentheses" node; the tree structure already captures the grouping.

Page 15

Building an AST

Let's take the parse tree for x = a + b * c and strip away the pieces that only helped the grammar express the syntax. What do we actually need for evaluation?

Parse tree

<assignment>
├── x
├── =
└── <expr>
    ├── <term>→a
    ├── +
    └── <term>
        ├── b
        ├── *
        └── c

AST

Assignment
├── x
└── Add
    ├── a
    └── Mult
        ├── b
        └── c

Gone are the <expr>/<term> nodes that were mainly there to encode precedence, along with the literal = token. What's left is the information we actually need: an assignment, an addition, a multiplication, and the identifiers involved.

The interpreter doesn't need to walk a grammar tree full of <expr>, <term>, and <factor> scaffolding. It wants the AST.

This is the kind of structure we'll eventually evaluate when we build the interpreter.

We've built the pieces by hand. Now we can name the whole process:

Page 17

Top-Down vs. Bottom-Up Parsing

Top-down

Starts from the root (the start symbol) and constructs the tree downward, toward the input tokens.

Bottom-up

Starts from the input tokens and constructs the tree upward, toward the start symbol.

Bottom-up parsers, including the LR family, are important in practice, but we won't implement one in this course. Our interpreter will use a top-down, recursive-descent approach. That's what we'll focus on next.

Page 18

Recursive Descent

Let's return to the precedence-aware grammar from earlier:

<expr> ::= <term> | <expr> + <term>
<term> ::= <id>   | <term> * <id>

First, we'll add one small piece: a <factor> level so parentheses have somewhere to go.

<expr>   ::= <term>   | <expr> + <term>
<term>   ::= <factor> | <term> * <factor>
<factor> ::= <id>     | ( <expr> )

Recursive descent gives each non-terminal its own function, calling the functions for whatever's nested inside it:

parse_expr()
↓
parse_term()
↓
parse_factor()
The grammar can directly guide the structure of the parser.

Each production rule maps naturally to a function, and the alternatives become branches inside that function. Once you see that connection, "writing a parser" becomes much less mysterious: you're translating a grammar you already know how to read into code.

Page 19

Building the Parser

Here's what parse_expr looks like when we translate that grammar into code:

def parse_expr():
    left = parse_term()
    while current_token == PLUS:
        advance()
        right = parse_term()
        left = BinaryOp('+', left, right)
    return left

Notice that it builds a BinaryOp node directly. The parser isn't just checking whether the input is valid; it's building the AST as it goes. parse_term() follows the same idea one level down, handling * instead of +.

Page 20

Grammar Constraints for Recursive Descent

Left recursion breaks this technique. Suppose we'd written our own <expr> rule the more "obvious" way:

<expr> ::= <expr> + <term> | <term>

A recursive-descent parse_expr() for this rule would call itself before consuming any token. It would recurse forever before making any progress. That's why our actual parser grammar avoids having <expr> as the first symbol on the right-hand side.

Lookahead: when a grammar offers several alternatives, the parser needs enough information from the next token to pick the right one. If a statement can start with an assignment, an if, or a while, seeing IDENTIFIER next means "try assignment"; seeing IF means "try the if-statement." We'll go deeper into this when we actually design the interpreter's parser.

Check Your Understanding

Six questions to check whether the main ideas from this topic have stuck. This isn't graded.

1
What's the difference between a derivation and a parse tree?
A derivation is the sequence of steps used to generate a sentence from the start symbol. A parse tree is the hierarchical structure that results — the same information, shown as a shape instead of a process.
2
A grammar is ambiguous if…
Not quite — nearly every useful grammar has multiple non-terminals. That alone doesn't make it ambiguous.
Correct — that's exactly what happened with our unfixed grammar and a + b * c.
Not quite — an ambiguous grammar generates plenty of valid sentences. The problem is some of them have more than one valid structure.
3
How does grammar structure encode operator precedence?
By nesting the higher-precedence operator's rule inside the lower-precedence one — like putting multiplication at the <term> level, one layer below addition's <expr> level. That nesting forces the tighter-binding operator to be built first, with no ambiguity possible.
4
Why would an interpreter prefer an AST over a full parse tree?
A parse tree is cluttered with grammar scaffolding — nodes for <expr>, <term>, <factor>, parentheses — that only existed to make parsing unambiguous. An AST keeps just the information needed to evaluate the program: what operation, on what operands. Much simpler to walk and evaluate.
5
Which parsing approach does the recursive-descent technique from this topic follow?
Correct — recursive descent starts from the start symbol (via parse_expr(), the outermost call) and works down toward the tokens.
Not quite — bottom-up parsers start from the tokens and build upward toward the start symbol. Recursive descent goes the other direction.
6
Why does left recursion break a recursive-descent parser?
A rule like <expr> ::= <expr> + <term> would make the function for <expr> call itself immediately, before consuming any token — infinite recursion with no base case ever reached. Rewriting the repetition to sit inside the rule instead of at its start avoids the problem entirely.

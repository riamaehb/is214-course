Functions & Abstraction

SYNTAX

what is valid

SEMANTICS

what it means

EXECUTION

what happens

Topic 6 established name → binding → scope → environment → closure. Now we can ask the next question: what happens when a name refers to a function, and what does the runtime have to do when that function is called?

Functions aren't just reusable blocks of code. They're values that can be called, passed around, returned, and associated with environments. The call environment is the central idea of this topic; recursion, higher-order functions, and closures will follow from it rather than appearing as separate features to memorize.

By the end of this topic, you should be able to

  • explain why a function is a value, not just a block of code;
  • distinguish parameters from arguments;
  • explain how a function call creates a new environment;
  • distinguish returning a value from printing one;
  • explain recursion in terms of separate call environments;
  • trace a higher-order function call;
  • distinguish a captured environment from a call environment in a closure; and
  • describe what an interpreter must do to execute a function call.

Estimated study time: 90–120 minutes.

What actually happens when square(5) is evaluated?

That question is what this whole topic is really about. Let's start with a distinction:

def square(x):      # definition
    return x * x

square(5)            # call

A definition creates a function value and establishes a binding between its name and that value — exactly the binding model from Topic 6. A call invokes that value. They're different events, and most of this topic is about what happens during the second one.

Functions as Values

def square(x):
    return x * x

f = square
f(5)
What does f refer to?

Not the number 25. f refers to the function itself. And f = square is an ordinary binding, just like y = x was in Topic 6:

f
↓
binding
↓
function value
A function can itself be a value.

This one idea is what makes higher-order functions possible later in the topic: a function is another kind of value that can be bound to a name, passed around, or returned.

Predict
Before evaluating anything else, what does add(2, 3) produce?
5 — but notice what had to happen first: x and y needed to be bound to 2 and 3 somewhere before x + y could be evaluated. That "somewhere" is exactly what the next page is about.

Function Calls Create Environments

This is the central idea of the topic. For:

def add(x, y):
    return x + y

add(2, 3)
Global Environment

↓ call
Call Environment
x → 2
y → 3 
x + y  →  2 + 3  →  5
A function call creates a new environment in which its parameters and local bindings are established.

This is the direct continuation of Topic 6. A call environment belongs to this specific invocation, and its parent links to the environment used to resolve names from the function's definition. Here that happens to be the global environment; later we'll see that it can be something more specific.

Return Values

    return x * 2

y = double(5)
double(5)
↓
10
↓
y → 10

So what does return actually do? It:

  1. evaluates its expression;
  2. produces a value;
  3. ends the current function call;
  4. gives that value back to the caller.
Page 7

Return vs. Print

def printed():
    print(5)

def returned():
    return 5

a = printed()
b = returned()
Predict
What does a refer to after a = printed()?
Not quite — printed() displays 5 on screen, but that's not the same as producing a value for the caller. Nothing was returned.
Correct — printed() never executes a return statement, so it implicitly returns None. The "5" you see is just output; it isn't the function's value.
Printing produces output. Returning produces a value for the caller.

This distinction matters directly for the interpreter you're building: an evaluator has to keep output behavior (a side effect) separate from the value an expression actually produces.

Page 8

Every Function Call Gets Its Own Environment

def add(x, y):
    return x + y

a = add(2, 3)
b = add(10, 20)

Call 1

x → 2
y → 3

Call 2

x → 10
y → 20
Each function call gets its own call environment.

Now apply that to a function that calls itself:

def factorial(n):
    if n == 0:
        return 1
    return n * factorial(n - 1)
factorial(3): n → 3
factorial(2): n → 2
factorial(1): n → 1
factorial(0): n → 0

factorial(0) → 1
factorial(1) → 1
factorial(2) → 2
factorial(3) → 6

The factorial algorithm itself isn't the point. The point is that every recursive call creates another call environment: four calls to the same function, four separate n bindings, none of them interfering with each other.

Page 9

Trace a Function Call

def add(x, y):
    z = x + y
    return z

result = add(2, 3)

Let's trace it in order:

  1. the function value bound to add;
  2. the call add(2, 3);
  3. the call environment it creates;
  4. the parameter bindings x → 2, y → 3;
  5. the local binding z;
  6. evaluation of x + y;
  7. the return value;
  8. the final binding of result.
Trace it
What is the final state — what does result refer to, and what happened to the call environment's z?
result → 5. Once add returns, its call environment is no longer needed for this call. The returned value, 5, is then bound to result in the caller's environment.
Page 10

Higher-Order Functions

Since functions are values, we can pass one as an argument:

def apply(f, x):
    return f(x)

def square(x):
    return x * x

apply(square, 4)
square is a function value. square(4) is the result of calling it. These are not the same thing.
Trace it
Trace apply(square, 4): what's bound to f? What's bound to x? What does f(x) mean inside apply? What's the final result?
f → square (the function value itself, not a call to it) and x → 4. Inside apply, f(x) means "call whatever function f is currently bound to, with argument x" — which becomes square(4), producing 16. Nothing about apply's code needed to know in advance which function it would be given.

If square were replaced by a different function, apply's code wouldn't need to change. That's the payoff of treating functions as ordinary values.

Page 11

Closures Revisited

Let's go back to Topic 6's make_adder — this time with a distinction we didn't need to draw there yet:

def make_adder(x):
    def add(y):
        return x + y
    return add

add5 = make_adder(5)
add5(3)
A closure is a function together with the environment it needs to resolve its non-local names.

There are actually two different environments involved here, and it's easy to mix them up:

Captured Environment (from make_adder(5))
x → 5
↓ parent
Call Environment (from add5(3))
y → 3
Captured environmentBelongs to the function value itself — created once, when make_adder(5) ran, and kept alive by add5.
Call environmentCreated fresh every time add5 is actually called — a brand new one for add5(3), with its parent pointing to the captured environment.

When add5(3) looks up x, the lookup fails in the call environment and then succeeds in the captured environment through the parent pointer. It's the same nested-lookup mechanism from Topic 6; the difference is that the parent here is a captured environment rather than the global one.

Page 12

Abstraction and Function Identity

Why do we use functions at all?
def calculate_total(price, tax):
    return price + price * tax

Whoever calls calculate_total doesn't need to know how it is implemented — only what it does. That's abstraction: functions let us decompose, reuse, parameterize, encapsulate, and compose pieces of a program without keeping all their internals in our heads at once.

There's one more distinction, already implicit in everything we've done:

fthe function value itself
f()invoking it

This is why a function can be passed as an argument or returned from another function: f alone is a value, ready to be handled like any other value.

Page 13

Trace a Closure

Here's the major synthesis activity for this topic: everything so far, in one example.

def make_multiplier(n):
    def multiply(x):
        return x * n
    return multiply

double = make_multiplier(2)
result = double(5)

Let's trace it in order:

  1. creation of make_multiplier;
  2. the call make_multiplier(2);
  3. the binding n → 2;
  4. creation of multiply, inside that environment;
  5. the environment multiply captures;
  6. the returned function value, bound to double;
  7. the call double(5);
  8. the new call environment it creates;
  9. the binding x → 5;
  10. lookup of n, through the captured environment;
  11. evaluation of x * n;
  12. the final result.
Trace it
What does result refer to at the end?
result → 10. double's captured environment holds n → 2. Calling double(5) creates a fresh call environment with x → 5, whose parent is the captured environment. Evaluating x * n finds x locally and n through the parent pointer, giving 5 * 2 = 10.

The Interpreter's Model of a Function Call

So what would our interpreter actually have to do when it encounters a function call?

Let's put everything from this topic together as the sequence an evaluator actually has to carry out:

AST: FunctionCall
↓
Evaluate function expression
↓
Evaluate arguments
↓
Obtain function value
↓
Create call environment
↓
Bind parameters
↓
Evaluate body
↓
RETURN RESULT

This is the direct bridge to the interpreter you'll build later: a function call isn't one mysterious step. It's this sequence, every time.

Page 15

Check Your Understanding

Nine questions to check whether you can apply the ideas from this topic. This isn't graded.

1 · Defining vs. calling
Between writing def square(x): return x * x and later writing square(5), what actually happens at each point?
The def creates a function value and binds it to square; nothing is computed yet. square(5) is a separate event: it invokes that function value, creating a call environment and running the body.
2 · Parameters vs. arguments
In def add(x, y): return x + y followed by add(2, 3), which are the parameters and which are the arguments?
x and y are parameters — names in the definition. 2 and 3 are arguments — values supplied at the call site and bound to those parameter names.
3 · Functions as values
Given f = square, what does f refer to, and why does that matter for passing functions around?
f refers to the function itself, not to the result of calling it. Because a function is a value, it can be bound to another name, passed as an argument, or returned from another function.
4 · Call environments
Why can't x + y inside add's body be evaluated before the call environment exists?
x and y are names, so evaluating them requires a lookup. Until the call creates a call environment and binds those parameters to their arguments, there is nowhere for that lookup to happen.
5 · Return vs. print
A function prints a value but never uses return. What does calling it actually produce as a value, and how is that different from what appears on screen?
It produces None. Printing is output — a side effect — and is separate from the value the function call evaluates to. What you see on screen and what the caller receives are two different things.
6 · Recursion
Looking back at the factorial(3) trace from Page 8: when factorial(0) is executing, how many active n bindings exist across the whole call chain, and why doesn't that cause confusion?
Four — one for each active call: factorial(3) has n → 3, factorial(2) has n → 2, factorial(1) has n → 1, and factorial(0) has n → 0. They don't interfere because each call has its own environment.
7 · Higher-order functions
In apply(square, 4), why is apply considered a higher-order function?
Because it takes a function (square) as an argument. It treats functions as values that can be passed around, rather than requiring one specific function to be hard-coded into its implementation.
8 · Closures
add5(3) involves two different environments at once. What are they, and how do they relate?
The captured environment from make_adder(5), holding x → 5, and a fresh call environment for add5(3), holding y → 3. The call environment points to the captured environment, so lookup can find x there.
9 · Abstraction
A caller uses calculate_total(price, tax) without knowing how it's implemented. What does that let the caller do that they couldn't do otherwise?
Use the computation by name, based on what it does, without needing to understand or repeat how it works. That's abstraction: larger programs can be built from pieces whose internal details don't all have to be kept in your head at once.
Final synthesis

If Topic 6 explains how names are resolved through environments, what does Topic 7 add?

Functions create new environments, receive values through parameters, produce values through returns, and can themselves be passed around as values.

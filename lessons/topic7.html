Functions & Abstraction

SYNTAX

SEMANTICS

what it means

Topic 6 established: name → binding → scope → environment → closure. This topic asks: what happens when a name refers to a function, and what does the runtime have to do when that function is called?

Functions aren't just reusable blocks of code — they're values that can be called, passed around, returned, and associated with environments. The call environment is the central idea of this lesson: everything else — recursion, higher-order functions, closures — follows directly from it, rather than being separate features to memorize.

By the end of this topic, you should be able to

  • explain why a function is a value, not just a block of code;
  • distinguish parameters from arguments;
  • explain how a function call creates a new environment;
  • distinguish returning a value from printing one;
  • explain recursion in terms of separate call environments;
  • trace a higher-order function call;
  • distinguish a captured environment from a call environment in a closure; and
  • describe what an interpreter must do to execute a function call.

Estimated study time: 90–120 minutes.

A definition creates a function value and establishes a binding between its name and that value — exactly the binding model from Topic 6. A call invokes that value. They're not the same event, and the rest of this lesson is mostly about what happens during the second one.

What does f refer to?

Not the number 25 — f refers to the function itself. f = square is an ordinary binding, exactly like y = x was in Topic 6:

A function can itself be a value.

This one idea is what makes higher-order functions possible later in this lesson — a function is just another kind of value that names can be bound to, passed around, and returned.

Function Calls Create Environments

This is the central idea of the entire lesson. For:

def add(x, y):
    return x + y

add(2, 3)
Global Environment
add → <function>
↓ call
Call Environment
x → 2
y → 3 
x + y  →  2 + 3  →  5
A function call creates a new environment in which its parameters and local bindings are established.

This is the direct continuation of Topic 6 — a call environment is an environment for this specific invocation, and its parent links to whatever environment is used to resolve names from the function's definition. Here that happens to be the global environment; later in this lesson, you'll see it can be something more specific.

Page 7

Return vs. Print

def printed():
    print(5)

def returned():
    return 5

a = printed()
b = returned()
Predict
What does a refer to after a = printed()?
Not quite — printed() displays 5 on screen, but that's not the same as producing a value for the caller. Nothing was returned.
Correct — printed() never executes a return statement, so it implicitly returns None. The "5" you see is just output; it isn't the function's value.
Printing produces output. Returning produces a value for the caller.

This distinction matters directly for the interpreter you're building — an evaluator has to keep output behavior (a side effect) separate from the value an expression actually produces.

Page 8

Every Function Call Gets Its Own Environment

def add(x, y):
    return x + y

a = add(2, 3)
b = add(10, 20)

Call 1

x → 2
y → 3

Call 2

x → 10
y → 20
Each function call gets its own call environment.

Now apply that to a function that calls itself:

def factorial(n):
    if n == 0:
        return 1
    return n * factorial(n - 1)
factorial(3): n → 3
factorial(2): n → 2
factorial(1): n → 1
factorial(0): n → 0

factorial(0) → 1
factorial(1) → 1
factorial(2) → 2
factorial(3) → 6

The factorial algorithm itself isn't the point. The point: every recursive call creates another call environment — four calls to the same function, four separate n bindings, none of them interfering with each other.

Page 9

Trace a Function Call

def add(x, y):
    z = x + y
    return z

result = add(2, 3)

Trace through, in order:

  1. the function value bound to add;
  2. the call add(2, 3);
  3. the call environment it creates;
  4. the parameter bindings x → 2, y → 3;
  5. the local binding z;
  6. evaluation of x + y;
  7. the return value;
  8. the final binding of result.
Trace it
What is the final state — what does result refer to, and what happened to the call environment's z?
result → 5. The call environment — with its x, y, and z bindings — is no longer needed for this call once add returns. The returned value, 5, is then bound to result in the caller's environment.
Page 10

Higher-Order Functions

Since functions are values, a function can be passed as an argument:

def apply(f, x):
    return f(x)

def square(x):
    return x * x

apply(square, 4)
square is a function value. square(4) is the result of calling it. These are not the same thing.
Trace it
Trace apply(square, 4): what's bound to f? What's bound to x? What does f(x) mean once inside apply? What's the final result?
f → square (the function value itself, not a call to it) and x → 4. Inside apply, f(x) means "call whatever function f is currently bound to, with argument x" — which becomes square(4), producing 16. Nothing about apply's code needed to know in advance which function it would be given.

If square were replaced by a different function entirely, apply's code wouldn't need to change at all — that's the payoff of treating functions as ordinary values.

Page 11

Closures Revisited

Back to Topic 6's make_adder — this time with a distinction Topic 6 didn't need to draw yet:

def make_adder(x):
    def add(y):
        return x + y
    return add

add5 = make_adder(5)
add5(3)
A closure is a function together with the environment required to resolve its non-local names.

There are actually two different environments involved here, and they're easy to conflate:

Captured Environment (from make_adder(5))
x → 5
↓ parent
Call Environment (from add5(3))
y → 3
Captured environmentBelongs to the function value itself — created once, when make_adder(5) ran, and kept alive by add5.
Call environmentCreated fresh every time add5 is actually called — a brand new one for add5(3), with its parent pointing to the captured environment.

Looking up x during add5(3) fails in the call environment, then succeeds in the captured environment via the parent pointer — the same nested-lookup mechanism from Topic 6, just now with the parent being a captured environment instead of the global one.

Page 12

Abstraction and Function Identity

Why do we use functions at all?
def calculate_total(price, tax):
    return price + price * tax

Whoever calls calculate_total doesn't need to know how it's implemented — just what it does. That's abstraction: functions give us decomposition, reuse, parameterization, encapsulation, and composability, all from the same mechanism you've been tracing this whole lesson.

One more quick distinction, already implicit in everything above:

fthe function value itself
f()invoking it

This is exactly why a function can be passed as an argument or returned from another function — f alone is just a value, ready to be handled like any other.

Page 13

Trace a Closure

The major synthesis activity of this topic — everything so far, in one example:

def make_multiplier(n):
    def multiply(x):
        return x * n
    return multiply

double = make_multiplier(2)
result = double(5)

Trace through, in order:

  1. creation of make_multiplier;
  2. the call make_multiplier(2);
  3. the binding n → 2;
  4. creation of multiply, inside that environment;
  5. the environment multiply captures;
  6. the returned function value, bound to double;
  7. the call double(5);
  8. the new call environment it creates;
  9. the binding x → 5;
  10. lookup of n, through the captured environment;
  11. evaluation of x * n;
  12. the final result.
Trace it
What does result refer to at the end?
result → 10. double's captured environment holds n → 2. Calling double(5) creates a fresh call environment with x → 5, whose parent is that captured environment. Evaluating x * n looks up x locally (5) and n through the parent pointer (2), giving 5 * 2 = 10.

Page 15

Check Your Understanding

Nine questions that ask you to apply this topic's ideas. Not graded — just for you to check where things stand before moving on.

1 · Defining vs. calling
Between writing def square(x): return x * x and later writing square(5), what actually happens at each point?
The def creates a function value and binds it to the name square — nothing is computed yet. square(5) is a separate event: it invokes that function value, which is when a call environment gets created and the body actually runs.
2 · Parameters vs. arguments
In def add(x, y): return x + y followed by add(2, 3), which are the parameters and which are the arguments?
x and y are parameters — names that exist in the definition. 2 and 3 are arguments — the actual values supplied at the call site, which get bound to those parameter names.
3 · Functions as values
Given f = square, what does f refer to, and why does that matter for passing functions around?
f refers to the function itself, not to any result of calling it. Because a function is just an ordinary value like any other, it can be bound to a new name, stored, passed as an argument, or returned from another function — exactly like a number or string could be.
4 · Call environments
Why can't x + y inside add's body be evaluated before the call environment exists?
x and y are names — evaluating them requires looking them up in some environment. Until the call happens and a call environment is created with those parameters bound to their arguments, there's nowhere for that lookup to even happen.
5 · Return vs. print
A function prints a value but never uses return. What does calling it actually produce as a value, and how is that different from what appears on screen?
It produces None — printing is output, a side effect, and has nothing to do with what value the function call itself evaluates to. What you see on screen and what the caller actually receives are two entirely separate things.
6 · Recursion
Looking back at the factorial(3) trace from Page 8: when factorial(0) is executing, how many active n bindings exist across the whole call chain, and why doesn't that cause confusion?
Four — one per active call: factorial(3) with n → 3, factorial(2) with n → 2, factorial(1) with n → 1, and factorial(0) with n → 0, all still on the way down. There's no confusion because each call environment is independent; they never interfere, even though they're all bindings for the same parameter name in the same function.
7 · Higher-order functions
In apply(square, 4), why is apply considered a higher-order function?
Because it takes a function (square) as one of its arguments — it operates on functions as data, not just on plain values. apply's own code never needed to know in advance which specific function it would be handed.
8 · Closures
add5(3) involves two different environments at once. What are they, and how do they relate?
The captured environment (from when make_adder(5) ran, holding x → 5) and a fresh call environment (created for this specific call to add5, holding y → 3). The call environment's parent pointer leads to the captured one, so a lookup for x during the call succeeds by following that link.
9 · Abstraction
A caller uses calculate_total(price, tax) without knowing how it's implemented. What does that let the caller do that they couldn't do otherwise?
Use the computation by name, based only on what it does, without needing to understand or repeat how it does it. That's the point of abstraction — it lets you compose larger programs out of pieces whose internals you don't have to hold in your head all at once.
Final synthesis

If Topic 6 explains how names are resolved through environments, what does Topic 7 add?

Functions create new environments, receive values through parameters, produce values through returns, and can themselves be passed around as values.

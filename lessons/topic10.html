Runtime, Interpretation & Python Execution

Nine topics have built up separate mechanisms: syntax, ASTs, semantics, values and types, environments, functions, control flow, objects and memory. This final topic asks the question that ties them all together: what happens between the program we write and the computation that actually executes?

The goal isn't compiler construction or Python implementation internals. It's a coherent runtime model you can use once you start building your own interpreter.

By the end of this topic, you should be able to

  • explain interpretation and compilation as implementation strategies, not fixed language categories;
  • describe what a runtime system is and what it's responsible for;
  • explain what an intermediate representation is, and why one might be used;
  • distinguish the evaluator from the runtime as a whole;
  • describe the runtime state a program needs while executing; and
  • explain how Topics 2–9 each contribute a piece of the runtime model.

Estimated study time: 90–120 minutes.

Illustrative pseudo-bytecode — not actual Python bytecode.
Why might a runtime execute an intermediate representation rather than the original source text?

An intermediate form can be simpler to execute quickly, easier to optimize, and independent of exactly how the source was written — the AST's shape doesn't have to be what actually gets run.

Page 8

What Does a Compiler's Back End Actually Do?

You've already seen Page 7's bytecode as a target representation. But where did it come from? A compiler doesn't just relabel the AST — it generates new instructions, and often rewrites them to run faster. Two techniques do most of that work.

Code generation walks the AST, or an intermediate form, and emits instructions for a target machine — real hardware, or an abstract one like a virtual machine. Page 7's bytecode is exactly this kind of output.

Optimization then looks for instructions it can improve without changing what the program computes. Take Page 7's own bytecode:

LOAD 2
LOAD 3
ADD
STORE x

Notice that 2 and 3 are literal values, known at compile time. An optimizer can compute 2 + 3 once, ahead of time, and emit just:

LOAD 5
STORE x

That's called constant folding — one of many optimizations a back end might apply. Others remove code that can never run (dead-code elimination), or avoid recomputing a value more than once.

Keep this at awareness level: the interpreter you build in this course stays an interpreter. It executes a representation directly, rather than compiling and optimizing it first. What matters here is knowing the back end exists, and roughly what it does — that's enough to place any given language implementation on the spectrum from Page 4.

Page 10

One Instruction Stream, or Many?

Every runtime model in this topic assumes one thing happens at a time — one runtime, executing one instruction stream, one step after another. Is that the only option? No. It's a design choice.

A language implementation can instead run multiple instruction streams at once:

  • threads — multiple streams sharing the same memory within one process;
  • processes — multiple independent runtimes, each with its own memory;
  • async tasks — many logical streams cooperatively interleaved on a single thread.

Python's own execution model, from the page before this one, has a well-known wrinkle here. CPython's Global Interpreter Lock (GIL) allows only one thread to execute Python bytecode at a time — even on a machine with many CPU cores. You can spin up multiple Python threads, but they take turns. They don't run Python code simultaneously.

So why do CPU-heavy Python programs often reach for multiple processes instead of multiple threads? Because separate processes each get their own interpreter, and their own GIL — so they really can run in parallel. Threads still earn their keep when a task spends most of its time waiting, for a file or a network response, rather than computing.

Keep this at awareness level. The interpreter you build in this course, like the runtime model in the rest of this topic, stays sequential — one stream, one step at a time. What matters is recognizing that this is a choice, and knowing what changes when it isn't.

Hands-On: Execution-Model Trace

x = 2
if x > 1:
    y = x + 3
print(y)

Work through, in order: the source representation, the relevant AST structures, which expressions must be evaluated, how the environment changes, which branch gets selected, and the final runtime state.

Trace it
Walk through all six, then check your answers.
1. Source: four statements — an assignment, a conditional, an assignment inside it, and a call.

2. AST structures: an Assignment node for x = 2, an If node with condition x > 1 and a body containing another Assignment, and a function-call expression for print(y).

3. Expressions evaluated: the literal 2; the comparison x > 1; the expression x + 3; the lookup of y when print is called.

4. Environment changes: x → 2 after the first line; y → 5 after the branch body runs.

5. Branch selection: x > 1 evaluates to True (2 > 1), so the if body executes — y gets bound.

6. Final runtime state: environment holds x → 2, y → 5; 5 gets printed.

Check Your Understanding

Eleven questions covering this topic. Not graded — just for you to check where things stand before moving on.

1 · Interpreter
What is an interpreter, conceptually?
Something that executes a program by processing a representation of it and carrying out the operations that representation describes.
2 · Compiler
What is a compiler, conceptually?
Something that translates a program from one representation into another — source into bytecode, or into machine code — that can then be executed or processed further, separately from the translation step itself.
3 · Strategies, not categories
Why are "interpreted language" and "compiled language" not fixed categories?
Because interpretation and compilation are implementation strategies, not properties baked into a language itself. The same language can have multiple implementations that choose different strategies — including ones that combine both, like compiling to bytecode and then interpreting that bytecode with a virtual machine.
4 · Runtime system
What is a runtime system responsible for?
Coordinating all the mechanisms needed to make a language's semantics actually happen during execution — environments and bindings, function calls, objects, memory, control flow, exceptions, and the execution of whatever representation the program has been turned into.
5 · Intermediate representation
What is an intermediate representation, and why might a runtime use one instead of the original source text?
A form the program gets translated into before execution — like bytecode — sitting somewhere between source code and final execution. A runtime might use one because it can be simpler or faster to execute, easier to optimize, and independent of exactly how the original source was written.
6 · Virtual machine
What is a virtual machine, conceptually?
An abstract execution environment for a program representation — it gives a language implementation a consistent target to run on, separate from the details of any one physical CPU, and can execute an intermediate representation directly.
7 · The evaluator's role
What's the difference between the evaluator and the runtime as a whole?
The evaluator is one component of the runtime — the part that determines the meaning or effect of a construct as it executes. The full runtime is bigger than that: it also has to manage environments, function calls, objects, control flow, exceptions, and memory.
8 · Runtime state
What kinds of runtime state does a program need while it executes?
At minimum: environments holding current bindings, objects with their own identity and state, and control state tracking what executes next. All three change as execution proceeds — that changing state is what "execution" actually consists of.
9 · Topics 6–9's contribution
In one sentence each, what did Topics 6 through 9 each contribute to this topic's runtime model?
Topic 6: environments and how names get bound and looked up. Topic 7: call environments and how function calls fit into that same model. Topic 8: control flow and how execution decides what happens next, including exceptions. Topic 9: objects, references, and how memory relates to what's still reachable.
10 · Compiler back end
What's the difference between code generation and optimization in a compiler's back end?
Code generation produces the target instructions from the AST or an intermediate form in the first place. Optimization then looks for ways to improve those instructions — like constant folding or dead-code elimination — without changing what the program computes.
11 · Sequential vs. concurrent execution
Why does CPython's GIL mean Python threads don't give CPU-bound code real parallelism?
The GIL allows only one thread to execute Python bytecode at a time, even with multiple threads and multiple CPU cores — threads take turns rather than truly running simultaneously. That's why CPU-bound Python code often uses separate processes instead, since each process gets its own interpreter and its own GIL.
Final synthesis

If an interpreter is an executable model of a programming language, what parts of the language have we already learned how to model?

Syntax, ASTs, semantics, values and types, environments, functions, control flow, exceptions, objects, references, memory, and runtime state — all ten topics, each contributing a piece of the model the interpreter project turns into something that actually runs.

Control Flow & Exceptions

SYNTAX

what is valid

SEMANTICS

what it means

EXECUTION

what happens

Topics 4–7 established how individual computations work: expressions produce values, values have types, names resolve through environments, and function calls create new environments. This topic shifts the question. Instead of what does this produce, it asks: which part of the program executes next, and why?

Control flow is the language's mechanism for deciding what executes next. Exceptions are part of the same idea: they provide another mechanism for changing the normal execution path.

By the end of this topic, you should be able to

  • explain control flow as the mechanism deciding what executes next;
  • trace conditional execution, including multiple branches;
  • trace for and while loops, and distinguish break from continue;
  • explain exceptions as a control-flow mechanism, not just an error message;
  • trace exception propagation across function calls; and
  • describe how an interpreter handles conditionals, loops, and exceptions differently from ordinary expressions.

Estimated study time: 90–120 minutes.

From Values to Execution

x = 10
if x > 5:
    print("large")
print("done")
Does every statement execute?

The last line always runs. The middle line depends on x. Change x to 3, and the printed output changes — nothing about the expressions themselves changed, only which ones get reached.

Multiple Branches

if score >= 90:
    grade = "A"
elif score >= 80:
    grade = "B"
else:
    grade = "C"
Predict
If score = 85, which branch executes?
Not quite — 85 is not ≥ 90, so this branch is skipped entirely.
Correct — 85 is not ≥ 90, but it is ≥ 80, so this branch executes and none of the others do.
Not quite — this only runs if neither prior condition matched, and 85 ≥ 80 does match.
A conditional chooses an execution path. It does not execute every branch.
Page 4

Boolean Decisions, Revisited

if x != 0 and 10 / x > 2:
    ...

You saw in Topic 4 that Python may not evaluate the second operand of and. Here, notice what that means for the execution path specifically: if x == 0, the 10 / x check never even runs — so no ZeroDivisionError, not because of any special handling, but because that part of the condition was never reached.

↓

↓

Boolean evaluation can determine whether part of a condition executes — and therefore affects the execution path.

Python truthiness

if 0: ...        # skipped
if 1: ...        # runs
if "": ...       # skipped
if "hello": ...  # runs

A condition doesn't have to literally produce True or False — Python uses truth-value testing, and different types define their own notion of "truthy" and "falsy."

Stepping back: languages differ in how they represent branching at all — but the underlying idea, evaluate a condition, choose one path, is what section 6 of a formal treatment would call selection. Same mechanism, different syntax across languages.

Iteration: Why Repeat?

print(1)
print(2)
print(3)
print(4)
What if this needs to happen 1,000 times?

Writing the same statement 1,000 times isn't just tedious — it doesn't even work if the count isn't known in advance. Iteration causes a block of code to execute repeatedly.

for i in range(4):
    print(i)

The focus here is the execution path — the same body running multiple times — not the specific syntax.

Page 8

Loop Tracing

x = 0
while x < 5:
    x += 2
Trace it
What values does x take before the loop exits?
0, 2, 4, 6. The condition is checked before each iteration: at x=0, 2, and 4 it's still true, so the body runs; at x=6, 6 < 5 is false, so the loop exits with x left at 6.
x = 1
while x < 10:
    x *= 2
Trace it
How many times does the body execute?
Four times: x goes 1 → 2 → 4 → 8 → 16. At x=8, 8 < 10 is still true, so the body runs one more time; at x=16, the condition is false and the loop exits.
Page 9

Loop Control: break and continue

for x in values:
    if x < 0:
        break
    print(x)
for x in values:
    if x < 0:
        continue
    print(x)
breakleave the nearest enclosing loop entirely
continueskip the rest of the current iteration, proceed to the next
In a for loop, continue moves to processing the next item. In a while loop, continue proceeds to the next condition check — not automatically the next item, since there may be no "next item" at all.
Predict
For values = [1, 2, -1, 3], what does the break version print?
Correct — the loop prints 1 and 2, then hits -1 and breaks out entirely. 3 is never reached at all.
Not quite — that's what the continue version would print. break leaves the loop immediately, so nothing after -1 ever runs.

One more step back: iteration is another language mechanism for controlling execution, the same way selection was. Selection chooses a path; iteration repeats one.

Exceptions

x = 10 / 0
What happens when evaluation cannot produce a normal result?

↓

↓

↓

An exception is a mechanism for changing the normal execution path when an exceptional condition occurs.

Not just "an error message" — a genuine change in what executes next, the same category of thing as a conditional or a loop.

Predict
In print("A"); x = 10 / 0; print("B"), does "B" ever print?
No. The exception raised at 10 / 0 interrupts the normal sequential path right there — execution never reaches the line after it, unless something catches the exception first.

Page 13

Exception Propagation

def divide(x, y):
    return x / y

def calculate():
    return divide(10, 0)

try:
    result = calculate()
except ZeroDivisionError:
    result = None
Where is the exception raised? Where is it handled?
calculate()
↓
divide()
↓
exception raised
↓
propagate outward
↓
handler found
↓
except block executes

The exception is raised inside divide, where there is no matching handler. It therefore propagates outward through the active function calls until a matching handler is found — the try/except surrounding the call to calculate() handles it. This connects to Topic 7: function calls form an active chain of execution, and an exception can transfer control across that chain.

Trace it
If divide itself had its own try/except ZeroDivisionError around x / y, would the outer try/except in this example still run its except block?
No. The exception would be caught right where it's raised, inside divide, and would never propagate any further — the outer try would see nothing go wrong at all. Propagation only continues past a function's boundary when that function itself doesn't handle the exception.

Page 15

Trace the Whole Execution Path: the Normal Path

The main synthesis activity of this topic, in two parts. First, a trace combining a function call, iteration, a conditional, continue, and a return:

def find_first_positive(values):
    for value in values:
        if value == 0:
            continue
        try:
            result = 10 / value
        except ZeroDivisionError:
            break
        if result > 5:
            return value
    return None

find_first_positive([0, 2, 5, 1])

The question at every step is the same: at this point, what executes next, and why?

Trace it
Trace through all four values in order, and give the final result.
value = 0: matches value == 0, so continue skips straight to the next value. value = 2: 10 / 2 = 5.0; result > 5 is False (5.0 is not greater than 5), so the loop continues. value = 5: 10 / 5 = 2.0; still not > 5, loop continues. value = 1: 10 / 1 = 10.0; 10.0 > 5 is True, so return value fires — returning 1. The function never reaches its final return None.

Notice the except ZeroDivisionError never fires here — and structurally, it never could in this function, since value == 0 is always caught by continue before the division ever runs. A handler being present doesn't mean it fires on every call. The next page traces a path where an exception genuinely does occur.

Page 16

Trace the Whole Execution Path: the Exceptional Path

A second, smaller example — this time the division by zero isn't filtered out first, so the exception path actually triggers:

def first_reciprocal_over(values, threshold):
    for value in values:
        try:
            result = 10 / value
        except ZeroDivisionError:
            break
        if result > threshold:
            return result
    return None

first_reciprocal_over([5, 0, 2], 3)
Trace it
Trace through this call and give the final result.
value = 5: 10 / 5 = 2.0; not > 3, loop continues. value = 0: 10 / 0 raises ZeroDivisionError. The except catches it, and break exits the loop immediately — value = 2 is never even reached. Execution falls through to return None.
Normal path: continue → iterate → return. Exceptional path: exception → handler → break → return.
Page 17

Control Flow in the Interpreter

What does an interpreter have to do differently for a conditional, loop, or exception than for an ordinary expression?

Conditional

AST: If
↓
evaluate condition
↓
choose branch
↓
evaluate selected branch

Loop

AST: While
↓
evaluate condition
↓ true
evaluate body
↓
repeat

Exception

evaluation
↓
exception raised
↓
search for handler
↓
found → execute handler · not found → propagate

An ordinary expression evaluates once and produces a value. A conditional has to choose which AST subtree to evaluate at all. A loop has to evaluate the same subtree repeatedly, checking a condition each time. An exception has to unwind — abandon the normal evaluation sequence and go looking for somewhere else to resume. These are structurally different jobs for the evaluator, not just different syntax.

Check Your Understanding

Eight questions that ask you to apply this topic's ideas. Not graded — just for you to check where things stand before moving on.

1 · Predict a branch
Given the grade example from Page 3, what does score = 90 produce?
Not quite — 90 ≥ 90, so the very first condition already matches.
Not quite — the first condition (score ≥ 90) is checked first and already matches at exactly 90, so the elif is never reached.
Correct — 90 ≥ 90 is true, so this branch runs and none of the others are even checked.
2 · Trace a loop
Trace x = 10, while x > 0: print(x); x -= 3. What values get printed?
10, 7, 4, 1. After printing 1, x becomes -2, and -2 > 0 is false, so the loop exits without printing a negative value.
3 · Compare break and continue
A loop needs to skip zero values but still process everything else, without stopping early. Which of break or continue fits, and why not the other one?
continue — it skips just the current iteration and moves on to the next, which is exactly "skip this one, keep going." break would stop the loop entirely on the first zero, which is too aggressive for "process everything else."
4 · Exception trace
In the calculate() → divide() example from Page 13, identify: where is the exception raised, and where is it handled?
Raised inside divide, at x / y when y is 0. It isn't handled there or in calculate, so it propagates outward through the active function calls until it reaches the try/except surrounding the call to calculate(), where it is handled.
5 · Exceptions as control flow
Why is it more accurate to call an exception a control-flow mechanism than to call it "an error message"?
Because what it actually does is change which code executes next — interrupting the normal path and transferring control to a handler (or terminating the program if none exists). Displaying information about the error is a side effect of that; the mechanism itself is about execution path, exactly like a conditional or a loop.
6 · Interpreter model — conditional
When an interpreter evaluates an If AST node, what does it do that it wouldn't do for a plain arithmetic expression?
Correct — a plain expression just evaluates. An If node has to decide, based on that evaluation, which of two possible subtrees to evaluate next.
Not quite — that would mean running code that shouldn't run at all, including code that might have side effects it shouldn't have.
7 · Interpreter model — exceptions
When an interpreter's evaluation of an expression raises an exception, what does the interpreter do next?
It abandons normal evaluation and searches outward for a handler — checking the current try block, then the caller's, and so on, propagating through the chain of call environments until a matching handler is found, or there's nowhere left to look and the exception terminates the program.
8 · Boundary with Topic 4
x != 0 and 10 / x > 2 — Topic 4 already explained why the second operand might not be evaluated. What does Topic 8 add to that same example?
Topic 4's focus was evaluation: whether the second operand gets evaluated at all. Topic 8's focus is execution path: what that skipped evaluation actually means for the program — namely, that the division by x never happens when x is 0, which is exactly why this pattern is used to avoid a ZeroDivisionError in the first place.
Final synthesis

If Topics 4–7 explain how computations are evaluated, how values are typed, how names are resolved, and how functions execute, what does Topic 8 add?

It determines which computation executes next, how execution branches and repeats, and how execution changes when an exception occurs.

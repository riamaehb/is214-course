Semantics, Expressions & Evaluation

SYNTAX

what is valid

SEMANTICS

what it means

EXECUTION

We have an AST. Now what does it actually mean, and how do we evaluate it?

Topic 3 gave us program structure. Now we need to give that structure meaning. And there's a second question hiding here: even if we know what an expression computes, we still need to think about when and how that computation happens.

By the end of this topic, you should be able to

  • explain the distinction between syntax and semantics;
  • explain what an expression is and how expressions are evaluated;
  • trace the evaluation of an expression represented as an AST;
  • describe operational, denotational, and axiomatic approaches to semantics;
  • explain why evaluation order matters, and identify side effects;
  • explain referential transparency;
  • distinguish eager and lazy evaluation, and explain Python's concrete short-circuit Boolean evaluation; and
  • implement a simple evaluator for a small AST.

Estimated study time: 75–100 minutes, including the hands-on activities.

Page 1

From Structure to Meaning

Topic 3 ended with an AST like this one, for x = a + b * c:

Assignment
├── x
└── Add
    ├── a
    └── Multiply
        ├── b
        └── c

Suppose a = 2, b = 3, and c = 4. Topic 3 tells us that the structure is valid. But what does this program actually do?

b × c → 12
a + 12 → 14

The result, 14, is then assigned to x.

Parsing gives us structure. Semantics tells us what that structure means. Evaluation is one way of carrying out that meaning.
Page 2

Syntax vs. Semantics

x = 2 + 3
SyntaxThe statement follows the language's rules for forming an assignment and an expression.
SemanticsIts meaning: evaluate 2 + 3, obtain 5, assign the result to x.
Syntax: "What structures are valid?" Semantics: "What do valid structures mean?"
Think about it
Consider 10 / 0. Is this syntactically valid? What's different about this problem compared to a syntax error?
The expression has a perfectly valid syntactic structure. Division of one number by another is grammatically fine. The problem only appears when we evaluate it. That's the distinction to keep in mind: being syntactically valid and being successfully executable are different questions.

An expression is a construct that can be evaluated to produce a value.

So expressions are essentially computations that produce values. The next question is the interesting one: how does that evaluation actually happen?

Page 4

Try It: Predict the Value

Before you run these in Python, predict what each one will produce:

2 + 3 * 4
(2 + 3) * 4
10 > 3
"hello" + " world"

Then actually run them in a Python shell and compare.

Think about it
Why did the first two expressions produce different results?
Because they produce different ASTs. 2 + 3 * 4 is structured as 2 + (3 * 4), while the parentheses in the second expression force (2 + 3) * 4. Evaluation works with the structure that parsing already established; it doesn't get to reinterpret it. This is Topic 3's precedence discussion showing up again.
Page 5

Evaluating an AST

Add
├── 2
└── Mult
    ├── 3
    └── 4

So how should an evaluator process this tree?

Step 1Evaluate the left child: 2 → 2
Step 2Evaluate the right child: Mult(3, 4), which requires 3 × 4 → 12
Step 3Evaluate the addition: 2 + 12 → 14

So: Add(2, Mult(3, 4)) → 14.

An evaluator recursively evaluates the parts of an AST and combines their results according to the meaning of each operation.

Page 7

A Tiny Evaluator

The process you just performed by hand can be written as a program:

def evaluate(node):
    if node.kind == "NUMBER":
        return node.value
    if node.kind == "ADD":
        return evaluate(node.left) + evaluate(node.right)
    if node.kind == "MULTIPLY":
        return evaluate(node.left) * evaluate(node.right)

For Add(Number(2), Multiply(Number(3), Number(4))), the evaluator recursively evaluates the children and returns 14 — exactly the trace you just worked through by hand.

The evaluator doesn't need to rediscover the syntax. The parser has already done that work and produced the structure. The evaluator's job is to give that structure meaning.

Page 9

Operational Semantics

Operational semantics describes the meaning of a construct in terms of the steps used to execute it.

x = 2
y = x + 3
1Evaluate 2 → 2
2Assign 2 to x
3Evaluate x + 3
4Look up x → 2
5Compute 2 + 3 → 5
6Assign 5 to y

The focus is: what steps happen during execution? This is particularly useful for thinking about interpreters, because an interpreter must ultimately carry out exactly such steps — it's the style of semantics closest to what you'll actually build.

Page 10

Denotational and Axiomatic Semantics

Operational semantics isn't the only way to describe meaning. There are two other perspectives worth knowing:

Denotational semantics

Maps a construct to a mathematical object or value. For 2 + 3, we might write its meaning as ⟦2 + 3⟧ = 5. The focus: what does this construct denote?

Axiomatic semantics

Describes behavior using logical statements about program states:

{ x > 0 }
x = x + 1
{ x > 1 }

The statements before and after describe properties that hold about the program's state. The focus: what can we prove about the state before and after execution?

Page 11

Three Ways of Describing Meaning

ApproachMain question
OperationalWhat steps does the program perform?
DenotationalWhat does the program mean mathematically?
AxiomaticWhat properties can we establish about program states?

You don't need to turn these into three definitions to memorize. The important point is the difference in perspective: semantics can describe meaning in terms of steps, mathematical meaning, or properties of program states.

Think about it
If we describe a program as a sequence of state changes during execution, which approach are we using?
Operational semantics — describing meaning as a sequence of execution steps is exactly what that approach is.

Evaluation Order

f() + g()

The expression has a structure, but one question remains: when does f() run, and when does g() run?

PrecedenceHow an expression is grouped — e.g. a + (b * c).
Evaluation orderWhen the parts of an expression are evaluated.

They're related, but they're not the same thing.

Try it yourself
def f():
    print("f")
    return 1

def g():
    print("g")
    return 2

f() + g()

Before running it: predict what will be printed, and in what order. Then run it and check.

Evaluation order is part of a language's semantics.
Page 13

Side Effects

An expression can do more than produce a value. A side effect is an observable change caused by evaluating it — for example, changing a variable, modifying an object, performing input/output, or raising an exception.

x = 0
def f():
    global x
    x += 1
    return x

The call f() produces a value and changes x. That's the important part.

Try it yourself

Before running f() + f(), predict: what value does the expression produce, and what does x contain afterward? Then run it. Next, run f() then f() as two separate statements and compare.

An expression can have both a value and an effect. This is why side effects make evaluation order matter.
Page 14

Why Side Effects Matter

Suppose two function calls both modify shared state:

f() + g()

If the calls happen in a different order, the final state can change too. It's not just the returned value that can differ; the program's state afterward can differ as well.

+
Evaluation order
↓
Observable program behavior

This is why understanding evaluation means looking at more than just the final value.

Page 15

Referential Transparency

An expression is referentially transparent if you can replace it with its value without changing the program's behavior.

2 + 3 can be replaced by 5 without changing anything. Now consider f() when the function changes program state. Can we always replace f() with 5 just because it returned 5 this time? Not necessarily. The call may also have changed state, and that effect would disappear if we made the substitution.

Think about it
Why is referential transparency useful when reasoning about programs?
Because expressions can be understood primarily through their values, rather than through hidden changes to program state elsewhere. You can reason about and substitute expressions based on their values without having to track hidden side effects. This is one reason the concept matters so much in functional programming.
Page 16

Eager and Lazy Evaluation

Eager

Evaluates arguments before passing them to a function.

f(g(), h())
→ evaluate g()
→ evaluate h()
→ call f(...)

Lazy

Delays computation until its result is actually needed.

One subtlety: eager evaluation tells us that the arguments are evaluated before the call. It doesn't, by itself, tell us whether g() or h() goes first. That is a separate evaluation-order rule.

Lazy evaluation can avoid unnecessary computation, but it also changes the question we have to ask when tracing a program: not just what gets evaluated, but when — or whether — it gets evaluated at all.

Page 17

Try It: Short-Circuit Evaluation in Python

Python gives us a concrete example of conditional evaluation through and and or.

def expensive():
    print("computed")
    return True

Predict, then run:

False and expensive()

Will "computed" print?

Now predict, then run:

True or expensive()
What happened?
In both cases, does Python call expensive()?
No. In both cases, Python skips expensive() because the result is already determined: False and ... must be False, and True or ... must be True. This is short-circuit evaluation — a concrete case where evaluation is delayed or skipped. It doesn't make Python a generally lazy language; this behavior applies to these Boolean operators.

Check Your Understanding

Six questions to put the ideas from this topic together. This isn't about memorizing definitions; use it to check whether you can reason through the concepts.

1 · Trace it
Trace this AST by hand: Multiply(Add(2, 3), Subtract(9, 4))
Add(2, 3) → 5, Subtract(9, 4) → 5, then Multiply(5, 5) → 25.
2 · Apply it
Take x = 10 / 0. What's syntactically valid about it, and what does evaluating it reveal?
Syntactically, it's completely fine — dividing one number by another is an ordinary valid expression, no grammar rule objects. The problem only shows up once you actually evaluate it: there's no valid value for division by zero. That's exactly why this kind of problem is only detectable during evaluation, not before.
3 · Apply it
For y = x + 1, describe its meaning three ways: operationally, denotationally, and axiomatically.
Operational: look up x, add 1, assign the result to y. Denotational: ⟦x + 1⟧ = the value of x, plus one. Axiomatic: {x = n} y = x + 1 {y = n + 1}.
4 · Apply it
Suppose f() adds 1 to a shared counter and g() doubles it. Why might f() + g() and g() + f() leave the counter in different final states?
Because both functions have side effects on the same shared state, evaluation order determines which side effect happens first. If the language evaluates the calls in the written order, the second function sees the state already changed by the first. Therefore, changing the order can change the final state even though the same two operations are performed.
5 · Apply it
In a fully eager language with no short-circuiting, what would False and expensive() do differently than it does in Python?
It would call expensive() regardless — printing its side effect and computing its return value — even though the overall result is guaranteed to be False no matter what expensive() returns. Python's short-circuiting skips that unnecessary work entirely.
6 · Diagnose
For each, identify where the problem is first detected — lexical analysis, syntax analysis, or evaluation: (a) x = 5 ? 2, (b) if x then y with no colon, (c) x = [1, 2][5]
(a) Lexical — ? isn't a valid token. (b) Syntax — every token is valid, but the arrangement isn't. (c) Evaluation — the structure is completely valid; the index just doesn't exist once the expression actually runs.
